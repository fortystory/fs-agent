# `grep`

`grep` 是内建的**只读**搜索工具：模型给一个正则，它扫会话工作区，逐行报出命中，形如
`相对路径:行号:文本`。它存在的第一理由是**权限账**——一次纯读取的搜索不该长得像一次可能写盘
的操作。来源是 [`.scratch/grep-tool/spec.md`](../.scratch/grep-tool/spec.md)。

## 为什么它不是一条 shell 命令

在它之前，模型要搜代码只有一条路：经 `bash` 拼一条 `rg` / `grep`。那条路上的两件事都不对。

- **权限代数**里，一次纯读取的搜索长得像一次可能写盘的操作：`bash` 的 `effect()` 恒为
  `Effect::Exclusive`（「一个 shell 什么都能写」）。于是默认的 `ask` 档下每次搜索都要打断人，
  `readonly` 档直接拒。
- **结果**全凭模型自己拼参数、自己决定截到哪儿——仓库里那套「超限落盘 + 头尾预览 + 指针」
  的约定它一点也拿不到。

`grep` 的 `effect()` 恒为 `Effect::ReadOnly`，买到的是两件事：

- **权限门**：四档对它都是 `Allow`（`readonly` / `ask` / `workspace` 一档、`auto` 一档），
  所以 `readonly` 档下它可用、`ask` 档下它不问人；
- **锁**：派发器只对 `Exclusive` 取工作区锁、对 `WritePaths` 取逐路径锁，`ReadOnly` 不取。

**它不承诺并发**：一批里只有 `task` 走 `Deferred`，其余按顺序跑——这条工具不改变调度器。

## 范围与忽略规则

- **只扫会话 cwd**：schema 里没有 `path` 参数，遍历范围写死在实现里（与 `repo_map` 同例）。
  于是一个不声明读路径、自己走 cwd 的工具完全绕开 `outside_read` 那套语义。
- **忽略规则就是 `ignore` 的默认**：遵守 `.gitignore`（含 `.ignore` 与 git 的全局忽略）、
  跳过隐藏文件与隐藏目录。这与 `rg` 的默认一致——换工具不该改变搜索结果。
  注意 `ignore` 的 `require_git` 默认开着：**不在 git 仓库里的目录，`.gitignore` 不生效**，
  这一点也与 `rg` 一致。
- **二进制不打印**：文件里见到第一个 NUL 字节就放弃它（`BinaryDetection::quit(0)`，rg 的
  默认那一档）。`grep-searcher` 自己的缺省是「照单全收」，那是刻意不用的那个值。
- **条目按路径排序**：同一个工作区上的输出稳定，模型与测试都少一件要猜的事。

## 参数面

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `pattern` | 是 | 要搜的正则（rg 语法）。大小写这类需求用内联语法解决，例如 `(?i)` |
| `glob` | 否 | 只搜匹配这个 glob 的文件，例如 `*.rs` |

- **只有两个参数**：工具声明是缓存前缀的一部分、一次定死，所以每多一个参数都是永久成本。
- **`glob` 只影响「搜哪些文件」**，不参与 pattern 的匹配；它由 `globset` 在遍历之后过滤。
  不用 `ignore` 自带的 `OverrideBuilder`：overrides 的优先级**高于** `.gitignore`，用它的话
  `glob` 会变成一条绕过忽略规则的逃生口（`glob: "ignored.txt"` 能让本该被忽略的文件重新被
  搜到）。这个参数只该缩小范围，不该放宽规则。
- **描述里有一句劝阻**：这是搜代码的首选方式，**不要用 `bash` 拼 `rg` / `grep`**。不写这一句，
  模型很可能继续拼 shell，上面那条权限收益一分也拿不到。

## 输出与上限

- **一行一条：`相对路径:行号:文本`**，路径相对会话 cwd（rg 的默认形状，省 token、模型熟）。
- **没有匹配时**返回一句如实的说明（「在工作区里没有匹配 `<pattern>` 的行」），而不是空字符串
  ——空结果与「工具坏了」在流上必须分得开。`glob` 什么都没选上时是另一句：「工作区里没有匹配
  glob `<glob>` 的文件」。
- **条数先收一刀**：一次调用最多列出 **500** 条（`MAX_MATCHES`，一个常量、不进配置），超出的
  部分不再收集、但继续数完，末尾写一行「还有 N 条未列出：请缩小搜索范围，或用 `glob` 只搜
  一部分文件」。这与仓库地图末尾那行「被省掉多少」是同一种收尾。
- **token 上限只有一条流水线**：`call()` 返回字符串，溢出、落盘与头尾预览全交给
  `context::truncate_result`。超过 `max_tool_result_tokens`（缺省 25 000）时整份结果落到
  `<会话目录>/outputs/<tool_call_id>.txt`（0600），事件里留头尾预览与指针
  （`[已截断：共 N 字符，约 M token；全文在 <路径>]`）。这条工具**不新增第二套截断**。
- **命中的文件不算「已读」**：`read_paths()` 是调用前的纯函数，声明不了运行时才知道的命中
  文件，所以搜到一个文件之后，`edit_file` 仍要求先 `read_file`。这是刻意的——要登记就得动
  `Tool` 接口，而这条工具不值得那次结构性改动。

## 为什么不 spawn `rg`

两条路线都评估过（[`research/01-search-tool-implementation.md`](../.scratch/grep-tool/research/01-search-tool-implementation.md)
的 §4 是五维对照），最后选自带库：

- **范围干净。** `rg` 经 `process::run` 跑起来继承的是沙箱的挂载表，而沙箱是
  `--ro-bind / /`：**整机可读**（除 `~/.config/fs-agent` 与 `~/.ssh` 两个遮罩）。那是
  「只读整机」，与 `Effect::ReadOnly` 的本意「只读**工作区**」不是一回事，`outside_read`
  也管不到它。自带库这条路的遍历范围就是代码里的 `ctx.cwd`。
- **没有新的运行期依赖。** spawn 路线把「工具能不能用」交给用户机器上有没有 `rg`，还要多出
  三件事：组装期探测 + 一条出路文案、`rg` 自己的配置文件会改行为（`RIPGREP_CONFIG_PATH`，
  要 `--no-config` 才关得掉）、退出码 1（无匹配）与 2（出错）要自己翻译。仓库已经容忍
  「首次构建慢」这一档代价（九个 tree-sitter C parser），所以这里选范围干净的。
- **输出可控。** 自带库拿到的是结构化的命中（路径、行号），于是上限、排序与那句「还有 N 条」
  都在我们手里；spawn 路线的 `-m` 是**每文件**上限，全局上限要自己读流早停，而早停拿到的
  退出码不可靠（ripgrep 把 BrokenPipe 当优雅退出 0）。

代价如实记下：`Cargo.lock` 多了十来个包（`ignore` + `grep-searcher` + `grep-regex` 与它们
的传递依赖，全是 `Unlicense OR MIT` 的纯 Rust 库），首次构建比纯文本处理慢一点。

## 与别的工具的分工

| 要知道什么 | 用哪个 |
| --- | --- |
| 这个工作区里定义了哪些符号 | **`repo_map`**——「有什么」 |
| 某个名字 / 模式出现在哪里 | **`grep`**——「在哪」 |
| 这个文件里到底怎么写的 | **`read_file`**——路径你已经知道 |

`bash` 一个字没动：它确实什么都能写，所以仍是 `Exclusive`；`grep` **不**禁用 `bash` 里的
`rg`，只是在描述里把模型引过来。执行者的工具表也照常拿到 `grep`（它不 `delegable() == false`）。
