# 终端标题：让一格终端看得见它在干什么

跑着 fs-agent 的终端标签/窗口标题现在写的是 `fs-agent` —— 那是终端按进程名自己填的，`src/` 里一行设置标题的代码都没有（`grep 'x1b]0|SetTitle|终端标题'` 零命中）。开三格终端跑三个目录，标题一模一样；切回来也看不出哪一格在跑、哪一格在等审批。

这次给 TUI 加上标题：**进 alt screen 时保存原标题，按状态写一条新的，退出时还原**。标题回答两件事：在哪个目录、在不在跑（以及跑哪个目标）。

来源：2026-10-01 一次 `/ask-matt` 里记下的种子（[`seed.md`](seed.md)），同日经 `/grill-with-docs` 折成这份 spec（八条决定：标题形状、状态词表、截断规则、目标名、设置点、还原、更新时机、只给 TUI 设）。

## 问题陈述

1. **标题没有信息。** 它由终端按进程名写上，既不含工作目录，也不含运行状态。
2. **多实例不可辨。** 同时开几个工作区时，标题全是 `fs-agent`。
3. **无人值守时最需要它。** 目标循环可能跑很久，人切到别的窗口去；回来第一眼看标题就知道它在推进哪个目标、还是卡在等你。
4. **没有往终端写 OSC 的先例。** 现有原始序列只有 DECSET 2026（同步更新）与鼠标/括号粘贴（[`src/render/tui.rs:401-404`](../../src/render/tui.rs)、[:426](../../src/render/tui.rs)），标题序列是这个仓库的第一个 OSC。

## 方案

- **形状**（§1）：`<路径> · <状态> · <目标名>`，三段按需省略；路径是 cwd 的 `父目录/基名`，`$HOME` 缩成 `~`。
- **状态**（§2）：空闲不带状态词；`运行中` / `等你` / `重放中` 三个词覆盖其余时刻。
- **封顶**（§3）：整条 40 列封顶，超了**从右往左丢**（先目标名、再状态词、再退成只剩基名）。
- **落点**（§4）：搭 `TerminalModes` 的车——它已经有 `enter()` 与 `Drop`（含 panic 路径），保存/还原标题住在同一处。
- **更新**（§5）：渲染器在绘制路径上比对一个标题快照，变了才写；不枚举事件源。
- **边界**（§6）：只给 TUI 设；`--plain` 与 headless 不设；不读终端响应。

## 用户故事

1. 作为开着几格终端的人，我希望每格标题显示它的工作目录，这样我能一眼找到对的那格。
2. 作为等模型干完活的人，我希望标题显示它还在跑、还是停在等我，这样我不用切回去看。
3. 作为跑目标的人，我希望标题显示当前目标的**名字**，这样我知道它在推进哪一件事。
4. 作为在很深目录里工作的人，我希望标题别被路径撑爆——该缩的缩、该丢的丢，而不是把状态词挤没。
5. 作为退出的人，我希望终端标题回到我原来那条，而不是永久被 fs-agent 占着。
6. 作为用 `--plain` 把输出接进脚本/日志的人，我希望它一个转义序列都不多发。

## 实现决定

### §1 标题的形状

- 三段，用 ` · ` 连接，**按需省略**：
  - `<路径>`（必有）
  - `<状态>`（空闲时省略，见 §2）
  - `<目标名>`（没有正在推进的目标时省略，见 §3）
- **路径**，两条分支：cwd 在 `$HOME` 之下 → `~` + **相对 `$HOME` 的完整路径**（`~/code/fs-agent`）；其余 → **父目录基名 / 当前基名**（`fortystory/fs-agent`）。cwd 就是 `/` 时写 `/`，cwd 就是 `$HOME` 时写 `~`。前缀按**路径分量**匹配，不做字符串前缀（`~/code2` 不是 `~/code` 的子路径）。
- 例：`fortystory/fs-agent · 运行中`、`fortystory/fs-agent · 等你`、`~/code/fs-agent · 运行中 · 修文档索引`、空闲且无目标：`fortystory/fs-agent`。
- **不做 prompt 摘要**：它要截断（截断多长又是一场讨论）、有把私密内容漏到窗口标题里的风险，而"在哪个目录、在不在跑"通常就够认了。

### §2 状态词表

四个时刻，三个词，优先级从高到低：

| 时刻 | 词 |
| --- | --- |
| 历史重放中（`state.replay.is_some()`） | `重放中` |
| 有任何问题立着（`state.pending.is_some()`：审批、问卷、目标停确认） | `等你` |
| 回合在跑（`state.busy()`） | `运行中` |
| 空闲 | 无（省略整段） |

- 优先级按上表：重放压过等你、等你压过运行中。「等你」把审批与问卷合一，因为对人来说那是同一件事：终端在等你。
- `muted`（禁言）不单独成词：它是运行中的一种，不该在标题里多一个词。
- 词进 [`src/render/wording.rs`](../../src/render/wording.rs)，与其它给人看的文本一起。

### §3 40 列封顶与丢弃顺序

- 整条标题按**显示列宽**（`text_columns`，不是字节）算，**40 列封顶**。
- 超了从右往左丢，一次一段：
  1. 丢 `<目标名>`；
  2. 再超，丢 `<状态>`；
  3. 再超，路径退成**只剩基名**（`~` 缩写仍生效）；
  4. 仍然超，硬截断到 40 列。
- 规则必须固定：标题没有宽度反馈，任何"看情况缩"的规则都无法测。

### §4 设置与还原：搭 `TerminalModes` 的车

- 落点是 [`src/render/tui.rs:422-450`](../../src/render/tui.rs) 的 `TerminalModes`：它已经有 `enter()`（进来时开鼠标与括号粘贴）与 `Drop` → `disable_terminal_modes()`（出去时关掉），并且 `enter()` 把 ratatui 的 panic hook 包了一层，让**崩溃退出也走同一条清理路径**。标题的保存与还原住同一处，因此 panic 时也会还原。
- **进入**（`enter()`）：先发保存序列 `\x1b[22;0t`（CSI 22 t，保存窗口标题），再发设置序列写第一版标题。
- **退出**（`disable_terminal_modes()`）：发恢复序列 `\x1b[23;0t`（CSI 23 t，恢复窗口标题）。
- 设置标题用 crossterm 的 `SetTitle`（0.29 有，它发的就是 `\x1b]0;…\x07`）；push/pop 没有对应命令，直接写序列（`execute!` 的先例在 [:401-404](../../src/render/tui.rs)）。
- 顺序无关：`ratatui::init()`（[:317](../../src/render/tui.rs)）在 `TerminalModes::enter()`（[:318](../../src/render/tui.rs)）之前，`drop(modes)`（[:412](../../src/render/tui.rs)）在 `ratatui::restore()`（[:413](../../src/render/tui.rs)）之前；标题是**窗口属性**，不是屏幕内容，早一步晚一步都不影响 alt screen 的进出。
- **不支持 push/pop 的终端**（部分 VTE 系）：两个序列是 no-op，标题会停在我们写的那条上。**接受这个退化**，不为它加 fallback —— 补发一条"清空标题"在不支持 push/pop 的终端上会把用户原本的标题抹掉，比不还原更糟。文档里如实记一句。

### §5 更新时机：绘制路径上比对快照

- `TuiState` 加一个 `last_title: Option<String>`。
- 在**绘制路径**上（主循环 [:397-405](../../src/render/tui.rs) 那段 `if state.is_dirty()`）算一次期望标题，与 `last_title` 不同才写 OSC，然后更新快照。
- 这样「只在状态变化时更新」自动成立，**不需要枚举事件源**——状态的来源有 `running`、`pending`、`replay`、目标名四处（分别由 `ConsoleRequest::RunState`、`request()`、`replay_batch()`/`finish_replay()`、目标事件推来），逐个挂钩一定会漏。
- 不逐 token 更新：标题要回答的是"这格终端在干嘛"，不是"它写到第几个字"；频繁写 OSC 在不少终端上看起来在闪。
- 渲染器要的另两样东西**不进 `SessionFacts`**（那会把它变成两个用途的混合体）：**cwd** 由 `TuiOptions` 随组装传进来（CLI 组装处已有该变量），**`$HOME`** 在 `Tui::run` 里读一次，两者进 `TuiState`。
- `TerminalModes::enter()` 写**第一版**并记下快照，绘制路径只管之后的变化——两处都写会重复发序列。

### §6 只给 TUI 设，且不进事件流

- 只有走 TUI 渲染器的会话会设标题。`Renderer::plain` / `headless` 不经过 `TerminalModes`，天然不设；**不特意为它们加代码**。`--plain` 的 stdout 可能被重定向，`headless` 的 stdout 只承载最终产物（[`docs/render.md`](../../docs/render.md)），都不该多出转义序列。
- 标题是**渲染器的副作用**，不进事件流：它不影响会话状态、不进 `log.jsonl`、`--continue` 不重建它（重开时按当时的 cwd 重新算）。
- 目标名靠**渲染器自己留一个字段**：目标事件本来就推到了前端，但转录层把 `GoalSelected` 丢掉了（[`src/render/transcript.rs`](../../src/render/transcript.rs)），`TuiState` 里没有它。在 `apply` 入口留一个 `goal: Option<String>`，遇到 `GoalStopped` / `GoalCompleted` 清掉；**不为标题新增会话事件**，`--continue` 的重放走同一条路径、自然重建。
- 不加配置项：标题内容固定，种子也没要求。

## 测试决定

- **纯函数**（[`tests/wording.rs`](../../tests/wording.rs)）：标题拼接与截断——形状（三段齐全 / 省略状态 / 省略目标名）、`~` 缩写、40 列封顶、三种丢弃顺序各一条、状态优先级各一条。
- **状态机**（[`tests/render_tui.rs`](../../tests/render_tui.rs)）：给 `TuiState` 一个可得标题的入口，断言 `busy` / `pending` / `replay` / 目标名四类状态下的输出；不碰真实终端。
- **终端序列**：`TestBackend` 不执行 `execute!`，所以 OSC 的验证只能靠 **pty 脚本** [`scripts/tui-startup-check.py`](../../scripts/tui-startup-check.py)。它已经有 TEARDOWN 序列检查的先例（[:76-83](../../scripts/tui-startup-check.py)、[:373-377](../../scripts/tui-startup-check.py)）：加一条「启动流里出现 `\x1b]0;` 且内容含 cwd 基名」与一条「退出流里出现 `\x1b[23;0t`」。
- **手工**（[`docs/tui-manual-checklist.md`](../../docs/tui-manual-checklist.md)）：新增一节，至少在 xterm、tmux、一个 VTE 系终端里各看一次：标题内容、状态变化时是否更新、退出后是否还原（或如实记录没还原）。tmux 下分别看 `set -g allow-passthrough` 开与关。
- **不测**：终端是否真的把标题显示出来——那是终端的行为，归手工清单。

## 明确不做

- 不做 prompt 摘要 / 任务摘要进标题。
- 不读终端响应、不查询原标题（一个装饰性功能不值得在启动路径上加一次可能阻塞的读）。
- 不给 `--plain` / headless 设标题。
- 不包 tmux passthrough 序列（`\x1bPtmux;…`）——tmux 对普通 OSC 有自己的一套，我们不猜用户的配置。
- 不加配置项、不做标题模板语法。
- 不改状态行 / 提示行里已有的任何文本。

## 补充说明

- 这条需求的**验收面大半在终端里**：能自动化的只有"我们发出了哪些序列"，"标题看起来对不对、还原没还原"必须手工。这一点与 [`docs/tui-manual-checklist.md`](../../docs/tui-manual-checklist.md) ⑦ 的精神一致（那里的终端交还也是脚本 + 手工两条腿）。
- 为什么不复用 `SessionFacts`：它是给面板与状态行看的事实集合，标题要的是**渲染器自己的状态**（pending/replay 只在 `TuiState` 里）。硬把标题塞进 `SessionFacts` 会让那个结构变成两个用途的混合体。
