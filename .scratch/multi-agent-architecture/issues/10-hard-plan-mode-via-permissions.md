# 硬 plan 模式：用权限档位实现，不新增状态机

Type: grilling
Status: resolved
Blocked by: 01, 05

## Question

ratify 第 9 条以"**模式 ≠ 工具**"解决了综述的内部矛盾：保留**硬 plan 模式**，砍掉 todo 工具。本票把实现路径定死。

综述（第 7 节）的证据链指向一个具体结论，值得完整引用：

> plan 模式正在变成**基础设施**而不是产品功能：Gemini CLI 的 plan 模式**默认启用**（`--approval-mode=plan`、`/plan [goal]`、Shift+Tab 循环，并用 `enter_plan_mode` / `exit_plan_mode` 两个**工具**进出）；opencode 的 plan 模式**干脆就是权限配置的产物**（把 `edit` 与 `bash` 设为 `ask`）。结论：**"禁写"这件事的正确实现位置是工具层的权限判定，而不是一个新状态机。**
>
> goose 走得更省：它把 ACP 的 `plan` 模式**映射到已有的 `Chat` 模式（工具全关）**，CLI 侧是 `/plan` 与 `/endplan`。

要回答：

1. **用哪条路线**：opencode 式（权限档位的一次预设）还是 goose 式（映射到已有的全关模式）？综述的结论是**不需要新状态机** —— 请确认这个结论，并说明它如何复用票 05 的权限门。
2. **进出方式**：工具（Gemini 的 `enter_plan_mode` / `exit_plan_mode`）还是手势（Shift+Tab / `/plan`）？还是两者都要？
3. **计划本身落在哪**。两个候选：**goose 的隐藏续跑提示** —— `/goal` 与 `/grind` 会往对话里注入**隐藏的 continuation nudge**（模型看到、用户不显式看到），综述称这是"想防跑偏但不想做 todo 工具时最便宜的做法，值得作为首选替代方案"；或 **OpenHands 的预设 agent** —— 一个只带 glob + grep + 一个只能写计划的 editor 的 agent，产出 `PLAN.md`。
4. **计划在 compaction 后是否重新注入**？Claude Code 会从磁盘重新注入。注意自动 compaction 是后置项。

**不要**做：`todo_write` 式结构化清单、每轮重新注入清单、计划审批流、用评审模型做目标验收（综述：OpenHands 的 `GoalController` 用一个 judge LLM + `max_iterations = 10`，那是比 todo 更强的一层，本图不做）。

**票 05 交接来的事实（2026-09-13）**：

- **权限门的裁决是封闭三态** `Allow | Ask | Deny`，门本身是**纯函数** `Policy → Verdict`（不读环境、不与人交互、不追加事件）。
- ⇒ 综述那句"禁写的正确实现位置是工具层的权限判定，而不是一个新状态机"**在机制上已被落实**：你的"硬 plan 模式"因此**不需要任何新机制**——它是**策略输入侧**的一个模式（与 `readonly` / `ask` / `auto` 并列，或由规则表达式表达"所有写操作 → `Deny`"），落到门上仍然只是产出三态之一。这直接回答你第 1 条的路线之问。
- 一条约束：hook **只能收紧、不能放松**（决策格 `Allow < Ask < Deny` 取上确界）。所以"用 hook 实现 plan 模式"可行，但**不能用 hook 放松** plan 模式的拒绝。
- 另：计划本身的落点（第 3 条）与 plan 模式**正交**——模式管"能不能写"，计划管"写去哪儿看"。别把两者耦合成一个机制。

## Answer

**已定（2026-09-13，grilling，6 问逐条确认）。** 机制底座来自票 05（门是纯函数、裁决封闭三态、模式是门的**输入**）；本票只定模式的形状与计划的落点。

### 1. 路线：opencode 式，判据落在 `SideEffect` 上（票面第 1 条）

**确认"不需要新状态机"，并给出精确判据**：

> **plan 模式 = 策略里的一条预设：对 `effect()` 不是 `ReadOnly` 的调用，一律 `Deny`。**

- **零新机制**：它直接落在票 03 的 `SideEffect` 枚举上。`ReadOnly` 工具（`read_file` / `glob` / `grep` / `repo_map` / `skill`）照常；`WritePaths` 与 `Exclusive`（`bash`）一律拒绝。
- **为什么是 `Deny` 而不是 opencode 的 `Ask`**：本票标题就是"**硬**"plan 模式。`Ask` 意味着每次都要问一遍，"硬"就不成立；要放行就退出模式。
- **为什么连 `bash` 也拒**：它的 effect 是 `Exclusive`（票 03 的定义就是"bash / 未知副作用"），shell 里能写文件——放它进来等于 plan 模式形同虚设。
- **否掉 goose 式（工具全关）**：那正是 ratify 第 9 条"**模式 ≠ 工具**"要避免的形状；而且它让模型**连读都不能读**——可"写一份有依据的计划"必须先探索代码。goose 在综述里是"更省"的对照，不是推荐。
- **否掉"用 hook 实现"**：技术上可行（hook 只能收紧），但 hook 是**用户的扩展点**，把内置模式塞进去会让内置模式依赖用户的配置是否存在；而且 hook 失败是 fail-closed，一个写坏的 hook 会让 plan 模式莫名其妙地阻断。
- **一条必须写死的推论**：**plan 模式的拒绝必须沿委派链继承**——否则"派一个执行者去写"就能绕过它。这要求票 20 的规则语言把 `Deny` 当作**可传播的约束**（"继承拒绝、不继承允许"）。

### 2. 进出方式：只用手势（票面第 2 条）

**`/plan` 与 `/endplan`（TUI 里 Shift+Tab 循环）；不进模型可见的工具面。**

- "**硬**"的含义是**用户不让写**，所以开关必须在用户手里。给模型一个 `exit_plan_mode`，等于把"能不能写"的最终决定交回给模型——那就不硬了。
- **不给 `enter_plan_mode` 也不亏**：用户想让它先规划就打 `/plan`；模型无法自行进入模式，也不需要。
- 而且这保住了"模式 ≠ 工具"：**模式不该出现在工具清单里**——工具清单进上下文、占 token，而它的**描述本身会诱导模型去调它**。

### 3. 计划落在 `PLAN.md`（票面第 3 条）

**落盘在项目根的 `PLAN.md`；plan 模式下对它的写入是策略里的唯一豁免。**

- **计划要活得比一次会话长**：`/endplan` 之后开始执行时，计划仍是"我们商定的东西"；而"一条助手消息"会在 compaction 里被裁掉——计划恰恰是最不该丢的那类内容。
- **它必须用户能看 / 能改 / 能提交**：模型计划写歪了，用户直接改文件比重新对话便宜。goose 的隐藏 nudge 用户看不见，也就无法纠正。
- **豁免的精确形状**：**不是**一条竞争的 `Allow` 规则，而是**deny 条件里的一个与项**（"非 `ReadOnly` **且** 写入集 ≠ `{<repo>/PLAN.md}`"）——因为票 20 选定的"忽略具体程度"语义下窄 `Allow` 压不过宽 `Deny`。
  - 必须是"**全部**路径"而不是"包含"：否则一个同时写 `PLAN.md` 与 `src/main.rs` 的调用就能借道。
  - `Exclusive`（`bash`）**不可豁免**：它没有路径集合，认不出目标。
- **否掉隐藏 nudge（goose）**：它至少得是一条事件（票 15 已定"注入内容必须记成事件"），所以"隐藏"只剩渲染层；而一条用户看不见的注入会让"模型为什么这么想"变得难以复现——那不如把计划本身写成文件。
- **否掉 OpenHands 的"预设 agent"**：那是**第三个 agent 身份**（只带 glob + grep + 一个只能写计划的 editor），而本图只有 `Debater` / `Executor` 两种身份；plan 模式是一个**模式**，不是身份。
- **与第 1 条正交**：模式管"能不能写"，计划管"写去哪儿看"。

### 4. compaction 之后不重新注入（票面第 4 条）

**不注入计划全文；只注入一条钉住的短指令指向文件。**

- **为什么"重新注入"这个动作根本不需要存在**：票 06 已定注入内容**钉住、永不被裁剪**——"计划在哪"这条指针本身不会因 compaction 消失。
- **全文常驻注入的代价很具体**：占每轮预算，而且**每次计划改动都会废掉前缀缓存**（票 06 的硬约束是"逐轮不变才保住缓存"）。指针是常量字符串，计划怎么改它都不变。
- 模型要全文就 `read_file`（票 07 已确认指针是个路径，不需要新工具）。
- 那条指令写成**祈使句**（"动手前先读 `PLAN.md`"）——票 09 已经证明"一行描述 + 按需加载"足够驱动模型。

### 5. `/plan` 撞上已存在的 `PLAN.md`：先问用户

**三选一：覆盖 / 追加 / 保留**（**仅在文件已存在时**才问）。

- **保留**：文件原样作为起点，模型在它上面编辑（可能先 `read_file`）。
- **覆盖**：**CLI 在进入时把文件清空**——这是用户刚刚点过头的销毁，也是唯一能让"从头写"不必先读的办法（票 03 的 read-before-write 对**已存在**的文件会拒写）。
- **追加**：文件保留，CLI 在末尾追加一条分隔（时间戳 + "以下为新一轮规划"），模型续写。
- **工具绝不擅自删用户的文件**；销毁只在用户显式选择时发生。
- **这不等于"计划审批流"**（票面明确不做）：问的是**已有文件的处置**，不是批准计划内容；内容的批准仍然是用户自己读了 `PLAN.md` 再决定是否 `/endplan`。

### 6. 模式不进事件流

**plan 模式的进出不是流上的事件；`--continue` 回到配置文件里的模式值。**

- 模式是 Session 的**策略值**（票 01：Session 持有 config / policy），不是流的内容。把策略状态塞进流会与 `config.toml` 形成**两个真相源**——而用户随时可以改配置。
- 审计真正需要的是**决策时刻的理由**，那已经由 `PermissionDecided.why` 承载，比"当时是什么模式"更直接；"何时进入过 plan 模式"也能从进入时注入的那条 `ContextInjected` 看出来。
- `--continue` **回到配置值**是更安全、也更可预期的立场：想继续规划就再 `/plan` 一次；"自动恢复上次的模式"等于把一个可能已经过期的意图强加给新会话。
- 因此**不给票 15 那个刚定死的 20 变体枚举加第 21 个变体**。

### 明确不做

- `todo_write` 式结构化清单、每轮重新注入计划清单、计划审批流、judge 模型做目标验收。
- `enter_plan_mode` / `exit_plan_mode` 工具（第 2 节）；goose 的隐藏 nudge 与 OpenHands 的预设 agent（第 3 节）；compaction 后重新注入计划全文（第 4 节）；`ModeChanged` 事件变体（第 6 节）。

### 交接

- **票 20**：plan 模式是规则语言必须能表达的**第一个真实用例**——"非 `ReadOnly` 的调用 → `Deny`" + 一条路径豁免；且 **`Deny` 必须可沿委派链传播**。
- **票 14**：执行者必须继承父级的 plan 模式拒绝（否则委派即是绕过）。
- **票 17**：那条指向 `PLAN.md` 的钉住指令是一条 `ContextInjected` 事件，投影要把它放进 `messages`（位置规则与 AGENTS.md / skills 同族）。
- **票 13**：状态栏要能显示当前模式（你的第 3 条已列了"权限模式"）；"覆盖 / 追加 / 保留"是进入模式时的一次**手势交互**，不是流上的事件。
- **票 19**：模式**不可查**（第 6 节），所以"这个调用为什么被拒"要以 `PermissionDecided.why` 为准——**不要去找一个"模式变更"事件**。

**票 20 交接来的答案（2026-09-13）**：你那条豁免**有了确切的表达形状，而且它不是一条竞争的 `Allow`**。

- **原因**（准备票 20 时发现的冲突）：Claude Code 的优先级语义是 `deny > ask > allow` **且忽略具体程度**——一条宽泛的 deny 压过一条精确的 allow。而你的形状是"宽泛 deny + 窄 allow"，所以**窄 allow 会被压掉**。
- **解决方式**：规则匹配的是**对这次调用的谓词**，不是工具名。于是你的豁免写成 **deny 条件里的一个与项**——"非 `ReadOnly` **且** 写入集 ≠ `{<repo>/PLAN.md}`"。它仍然是一条"一律拒绝"，只是拒绝的定义更精确。
- **你要求的"路径集合恰好等于"就是 `Scope::PathSet(exact)`**（票 20 第 1 节）。票 20 明说它不是可选加强：只有路径通配的话，那个豁免写不出安全的形状。
- 另：**`Deny` 默认沿委派链传播**（票 20 第 3 节，按动作定默认值）——所以你那条"派执行者去写不是绕过路径"自动成立，不需要额外约定。
