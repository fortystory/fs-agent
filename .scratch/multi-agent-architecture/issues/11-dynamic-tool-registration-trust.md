# 动态工具注册与「只读」标记的可信度策略

Type: grilling
Status: resolved
Blocked by: 03, 05

## Question

ratify 第 3 条翻案把「自定义工具注册」加进了范围。**这一条与已定的扩展档位 (iii) 直接冲突** —— (iii) 的原文是"**不**做配置驱动的动态加载（MCP / 插件）"。所以档位已被 superseded 为「hook 挂载点 **+** 动态工具注册」。本票要把新增的那一半定形。

**本票的核心不是"怎么加载"，而是"加载进来的东西能不能被信任"。**

1. **可信度策略（必答题）。** 工具面一旦不再编译期封闭，「只读」这个副作用标记就成了**不可信输入**。而并行判定规则是「按有无副作用打标，只读并发、有副作用串行」—— 综述从**五个独立数据点**收敛出的共识（Claude Code 明文规则、Gemini 默认并发但强制 `replace`/`write_file` 串行、Codex 默认串行、Cline 按模型家族开关、Continue 只对只读开放）。一个动态注册的工具**谎报只读**，就会让两个写操作并发。
   候选策略：
   - (a) 动态工具**一律默认串行**，只读需显式声明 + 首次人工确认；
   - (b) 声明即信任（明确放弃这条防线，并在文档里说清）；
   - (c) 动态工具**不可并发**，其副作用标记不参与并行判定。

2. **声明格式。** 综述的候选是「额外工具 = 一个 shell 命令 + 参数 schema」。schema 用什么表示（JSON Schema？）？与票 03 的内建工具注册表是**同一个数据结构**，还是两套？

3. **命令的解析与权限。** 动态工具最终落到 shell 命令，那么综述第 5 节那条「**用语法分析而非字符串匹配**来判定 bash 权限」（opencode 用 tree-sitter 解析命令 + 一张 arity 字典）是否也适用？还是说动态工具被视为受信任的本地扩展、走另一条路？

4. **命名空间。** 综述的反向警告：「工具一多模型越容易选错」；Anthropic 建议做命名空间（Amp / Claude Code 都用 `mcp__<server>__<tool>`）与工具合并。约定要不要现在就定？

5. **明确不做**：**MCP client 本身**（ratify 第 2 条已砍）。本票只做"本地声明的自定义工具"，不实现 MCP 协议。

**票 09 交接来的一个设计选项（2026-09-12）**：Amp 的反直觉建议——**不要把额外工具全局挂着，而是打包进 skill**，因为"工具一多模型就选错"，且 skill 提供的工具在 skill 加载前对模型**不可见**。v1 的 skills 只有指令（票 09），所以"按需让工具可见"这条留给了本票：动态注册的工具是**启动即全局可见**，还是**挂在 skill 上、加载才可见**？这与本票的可信度策略相互作用（不可见的工具连被误用的机会都没有）。

**依赖说明**：必须在票 03（内建工具 trait / 注册表 / 副作用标记）与票 05（hook 与权限门的次序）之后 —— 可信度策略是在权限门里执行的，声明格式复用 03 的注册表。

**票 03 交接来的具体接口（2026-09-12）**：内建工具的副作用类别由 `Tool::effect(&self, args) -> SideEffect` 在**编译期常量**层面确定（只读工具无条件返回 `ReadOnly`），可信。**动态工具的同一个方法返回什么，就是本票的必答题**：是由声明推导（例如"shell 命令一律 `Exclusive`"）、声明即信任、还是强制不可并发。相关的既有接口：`ToolRegistry::register(Box<dyn Tool>)` 是唯一挂载点；args 是 `serde_json::Value`；`ToolSpec`（name/description/JSON Schema）内建与动态**同一套**（票 03 第 2 节）。

## Answer

**已定（2026-09-13，grilling，4 问一轮确认）。** 挂载点（`ToolRegistry::register`）与线级形状（`ToolSpec`）来自票 03；调用次序与权限门来自票 05。

> **本票的重心被搬了一次**：票面说"核心不是怎么加载，而是加载进来的东西**能不能被信任**"。答案把这句话**取消**了——动态工具的声明里**没有"只读"这个字段可填**，所以"谎报只读"不是一个需要防的攻击，而是一个**说不出口的谎**。

### 1. 可信度：`effect()` 恒为 `Exclusive`（票面第 1 条）

**动态工具的 `effect(&self, args)` 永远返回 `SideEffect::Exclusive`。**

- **为什么这不是"选择不信任"，而是"没什么可信任"**：动态工具声明的是**一条命令 + 参数 schema**；它**不声明副作用类别**。`ReadOnly` 这个值在动态工具的声明语法里**不存在**——谎报需要一个可填的字段，没有字段就没有谎（与票 05 的"放松意图在类型里不存在"同一手法：**非法状态不可表示**）。
- **为什么不是"只读需显式声明 + 首次人工确认"**：那要多出一个**需要审计的声明字段**、一次交互流程、一张"已确认"状态表；而收益只是让部分动态工具能并发——**票 03 已定 v1 默认整批串行**，所以并发收益在 v1 是**零**。等真开并行再说，那时也该先有真实数据。
- **为什么不是"声明即信任"**：它把"两个写操作并发"当成可接受的文档风险，而我们有一条**零成本**的替代。
- **代价诚实说**：一个真正只读的动态工具也会全局串行（`Exclusive` 按票 03 会取"工作区锁"）。可以接受：动态工具是逃生口，不是热路径。
- **一条必须写明的副作用**：**`read-before-edit` 对动态工具不生效**——它的 `WritePaths` 未知，所以票 03 那道"改文件前必须先读"的护栏**覆盖不到它**。这正是动态工具应当"保守 + 可被规则约束"的理由（第 2 节把约束落在权限门上）。

### 2. 声明与执行（票面第 2、3 条）

**同一套 `ToolSpec`**（票 03 第 2 节：name / description / JSON Schema），动态工具只多一个**命令模板**字段。声明住在 `~/.config/fs-agent/config.toml`（map 的 Notes）。

```toml
[[tools.custom]]
ns          = "gh"
name        = "list_prs"
description = "列出某个仓库的 PR"
parameters  = { type = "object",
                properties = { repo = { type = "string" } },
                required   = ["repo"] }      # JSON Schema：原样就是 provider 的 tools[].function.parameters
command     = ["gh", "pr", "list", "--repo", "{repo}", "--json", "number,title"]
timeout_ms  = 20000
```

- **零翻译**：`parameters` 的 JSON Schema **就是**票 02 的线级形状，不需要第二套 DSL 再翻译一次（两套 schema 会漂移）。
- **执行形态：argv 数组，不经 shell。** 参数按**整个 argv 元素**替换。
  - **它直接消灭 shell 注入**：模型控制的是参数值，而参数值永远不会被 shell 解释（没有 `;`、`|`、`$()`、反引号）。
  - **它把票面第 3 条那个问题消掉了**：综述第 5 节说 opencode 用 tree-sitter 解析命令 + arity 字典判定 bash 权限——那是在**防模型拼出一条危险命令**。我们的动态工具**不让模型拼命令**（命令是用户声明的、固定的），所以那套分析**在动态工具上完全不适用**；它要适用也只适用于**内建 `bash` 工具**（归票 20）。
  - 需要管道 / 重定向的场景：用户在**自己的脚本文件**里写，声明指向那个脚本（`["/path/to/my.sh", "{repo}"]`）——而不是让 harness 拼 shell 字符串。
- **参数替换的精确规则**：缺席的可选参数 ⇒ **整个 argv 元素省略**；数组 / 对象参数 ⇒ **JSON 序列化成一个 argv 元素**（**不展开**成多个，否则"一个参数变多个 argv 元素"会立刻变成注入面）。
- **参数先按声明校验**（JSON Schema），失败 → `ToolError::InvalidArgs`（票 03 已有该变体）。
- **仍然过权限门**（票 05）：动态工具与内建工具走**同一条** `hook.pre → 权限门 → dispatch → hook.post`；`effect()` 是 `Exclusive`，策略**按声明的名字**匹配。所以"动态工具一律 `Ask`""只允许某几个""某个 → `Deny`"都能用**既有机制**表达。
- **不是"受信任的本地扩展走另一条路"**：命令的**声明**是用户配置（可信），但**每次调用**照旧被权限门审；argv 只是让**命令本身**不可被模型操纵。
- **必须有超时与进程树终止**：动态工具是**外部进程**，挂住它就是挂住整个 turn（与票 05 对 hook 用的是同一条理由）。`timeout_ms` 可声明覆盖，有默认值（具体数字 → `/to-spec`）。
- **非零退出 = 一条错误内容的工具结果**（票 03 的 `Result` 路径 + 循环合成）；stdout 是模型可见内容，stderr 在失败时一并给出。

### 3. 命名空间：现在就定（票面第 4 条）

**动态工具名 = `custom__<ns>__<tool>`**（上例即 `custom__gh__list_prs`）。

- **理由一（最有用）**：**内建工具名永不含 `__`**，于是"名字里有 `__` ⟺ 是动态工具"成为一个**词法上可判定的谓词**——权限规则、渲染、可观测性都能一眼区分来源，**不用查注册表**。
- **理由二**：与生态既有约定（`mcp__<server>__<tool>`）同形；将来真接 MCP 只是把前缀换成 `mcp__`，形状不变。
- **理由三**（针对"工具一多模型选错"）：命名空间让同类工具在**名字上聚在一起**，这是模型选对的最便宜线索。
- **工具合并 / 拆分不做**：声明是用户写的，"哪些工具放一起"是他自己在配置里的决定。

### 4. 可见性：启动即全局可见（票 09 交接）

**工具集在组装期固定、随 Session 走**（票 03 的注册表本来就是"运行期值、组装期构造"）。

- **决定性理由是缓存前缀**：`tools` 数组是请求**前缀**的一部分（票 02 的线级形状 + 票 06 的"逐轮不变才保住前缀缓存"）。**中途增删工具 = 前缀变化 = 丢掉那张"免费的 5~10 倍成本差"**。票 09 的 skill body 之所以能安全地按需加载，正是因为它追加在**尾部**——工具做不到这一点。
- **Amp 的顾虑用已有的机制接住**：一个动态工具**能不能被调用**是**权限门**的事（规则），不是"可见性"的事。要禁就写一条 deny；要"只在某个 skill 里才用"，就需要权限门的输入里能看见"当前加载了哪些 skill"——**那是一个接口问题，交接票 20**（一个真实的设计选项，但不要为了它把工具数组变成动态的）。
- **"工具一多模型选错"的缓解**：命名空间（第 3 节）+ 描述纪律 + **工具是用户自己声明的**（多是他自己配的）。
- 代价诚实说：模型每一轮都会看到全部动态工具的描述——这是用户为"扩展性"付的 token，换来的是**前缀稳定**。

### 明确不做

- **MCP client 本身**（ratify 第 2 条已砍）：本票只做"本地声明的自定义工具"，不实现 MCP 协议。
- 动态工具声明副作用类别（第 1 节）、shell 字符串命令与随之而来的命令解析防线（第 2 节）、自动工具合并（第 3 节）、按 skill 的可见性开关（第 4 节）。

### 交接

- **票 03**：`effect()` 的必答题有答案了（恒 `Exclusive`）；另有一条你需要知道的后果——**`read-before-edit` 覆盖不到动态工具**（`WritePaths` 未知）。
- **票 09**：你交接的可见性选项已定——**启动即全局可见**，理由是 `tools` 数组属于**前缀**、中途变化会废掉缓存（skill body 追加在尾部才安全）。
- **票 20**：动态工具是权限规则的**普通目标**，按声明名（`custom__ns__tool`）匹配；另有一个真实选项：想让某工具"只在某 skill 加载后可用"，需要门的输入里能看见**已加载的 skill 集合**。
- **票 19**：`__` 谓词给你免费的来源区分（"哪些调用来自用户自定义工具"）；动态工具的超时与失败也各有事件形状（`ToolCallCompleted{ok:false}` + `SessionError`）。

**票 20 交接来的答案（2026-09-13）**：你第 104 行交给票 20 的那件事（"执行信任策略的地方是权限门"）答案是——**门这一侧不需要任何额外策略**。

- **因为你把这个问题本身取消了**：动态工具的声明语法里没有副作用类别字段，`effect()` 恒为 `Exclusive`。所以**没有一条"不信任动态工具"的特例规则**，它就是**普通目标**。
- **你的命名约定直接可用**：规则的作用域支持 `Tool(glob)`（票 20 第 1 节），所以 `Tool("custom__*")` **一条规则**就兜住"我新加了个自定义工具、忘了配规则"这个真实事故——这正是你第 3 节那个词法谓词的第一个真实用户。
- **你那个"可选接口"（让某工具只在某 skill 加载后可用）票 20 没做**：门是纯函数、不读环境（票 05），而"当前加载了哪些 skill"是会话状态。如果将来要做，它是**给门的输入加一份状态**，不是一个规则形状问题。
- 一条边界确认：**`task`（派发）不属于 `WritePaths`/`Exclusive`**（票 14 的语义澄清），所以写"所有写类工具都要 `Ask`"时 `task` 不在那一类里——而它派出的执行者内部的写会各自过门。
