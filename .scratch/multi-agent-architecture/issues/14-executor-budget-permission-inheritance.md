### 1. 执行者的形态与模型（票面第 1 条）

**v1 = 一个通用 `task` 工具；模型默认继承派出它的那个讨论者，可配覆盖。**

- **为什么不做"专职角色"**：本图只有两种身份（`Debater` / `Executor`，`CONTEXT.md` 已定），专职角色会引入**第三种身份概念**，而 v1 没有真实需求。而且综述里子 agent 的 system prompt 本来就是**独立的、更短的**——所以"角色"本质上是**配置**（模型 + prompt），不是代码结构。
- **未来的挂点已经存在**（不预留字段，与票 04 拒绝 `edit_format` 同一条）：`task` 的 args schema 加一个 `role` 字段 + 组装期按 profile 构造（票 03 的 `builtin()` 是函数、注册表是运行期值）。
- **模型默认继承派出者**：零配置、最不意外；在异构讨论里也保持了视角一致。可配覆盖。
- **身份不进流**（Chart 期已定）：执行者的 system prompt 私有，只出现在它自己的请求里。
- **执行者的上下文注入**：它是同一个仓库里的一个 Session ⇒ **`AGENTS.md` 与 skill 描述清单照常注入**（仓库规则对它同样适用）；**不带讨论协议相关的注入**（它不参与讨论）。plan 模式下那条钉住的短指令随 plan 模式一起继承。

### 2. 独立预算（票面第 2 条）

**执行者有自己的轮数上限，默认 25（goose 的 `GOOSE_SUBAGENT_MAX_TURNS`），可配。**

- 综述的硬结论：不独立预算，一个跑飞的子 agent 会吃掉整个会话的轮数配额。**这是需求，不是优化。**
- 25 比会话级的 100（票 02）小一个量级——执行者是"干活"，不是"长跑"。
- **结构上零新机制**：票 06 已定"预算按 agent 各自模型算、无全局预算"，执行者就是一个带自己模型的嵌套 Session，公式直接适用。
- **但"独立"只指轮数，不指钱**：它的 token 花费**仍计入会话累计**（票 06 的"会话累计是从 `Usage` 事件求和的派生值"），所以票 18 的成本闸门看得见它。
- 撞墙时 `TurnEnded { reason: MaxIterations }` 记录（票 13 第 4 节要求理由带上"撞的是哪个上限"）。

### 3. 权限继承、深度与 read set（票面第 3、6 条 + 票 03 交接）

- **继承拒绝、不继承允许**（opencode 的形状）。理由：**拒绝是一个约束，约束沿链传播只可能变严**——与票 05 的"hook 只能收紧"、票 10 的 plan 模式是**同一个代数**。允许不继承，因为"父级能做"不该自动授权子级。
- **票 10 那条硬要求因此自动满足**：plan 模式的拒绝就是一条 `Deny`，它沿链传播，"派执行者去写"不再是绕过路径。
- **递归深度默认 1：执行者不能再派执行者**——而且第一道防线是**它的工具集里没有 `task`**（不是"有工具但规则拒绝"）：工具不存在，模型连试的机会都没有。组装期用不同的 `builtin()` 结果即得（票 03 的注册表机制）。
- **read set 不继承**（回答票 03 的交接问题）：`read-before-edit` 防的是"凭想象改文件"，而"想象"是**每个 agent 各自**的——父读过不等于子见过，子改一个自己没看过的文件正是事故形态。所以嵌套 Session 的 read set **从空开始**，**任一方向都不流动**（父也不继承子的）。
  - 代价：多几次读（token）。买的是护栏的语义完整性——而且它比"合并两个 read set"**更省实现**。

### 4. 回传什么，以及谁看得见（票面第 4 条 + map 的雾）

**回传摘要 + 元数据；过程默认不进任何讨论者的窗；结论经派发者自己的发言进入讨论。**

- **回传的内容**：
  - **摘要** = 执行者自己的最终文本（`ExecutorFinished { summary }`，同时是那次 `task` 调用的工具结果——见第 5 节）。
  - **元数据**：token / 花费（`UsageRecorded` 已在流里）、**它改了哪些文件**（从流上那次 Session 的 `ToolCallStarted` + 编辑类调用**推导**，不需要新字段）。
- **可见性策略（雾里那条的答案）**：**默认只把结论给讨论者，过程默认谁都不进**。
  - 机制是现成的（票 15）：投影规则按 `SpeakerId::Executor(id)` + 事件种类过滤。
  - 理由一（硬数字）：综述里 Claude Code 的子 agent 读了 6.1k tokens，而主上下文只增 420——**"只回传结论"是省 token 的主力**。
  - 理由二：异构讨论的多样性靠的是两个讨论者**各自的观点**；一个执行者的**过程不是第三种观点**，灌进两个人的窗口只会稀释它。
  - **结论怎么进讨论**：通过**派发者自己的话**（"我让它查了 X，结果是 Y，所以…"）。讨论传的是**发言**，不是共享的工具历史。
  - **对派发者与其他讨论者一视同仁**：不让派发者额外拿到原始输出，否则在讨论者之间制造**信息不对称**，而票 16 的独立首轮正是要避免互相影响。
  - 反方诚实说：综述指出"只暴露结论"**没有消融证据**。所以这是**默认 + 可 zoom**，不是硬隔离——要看 raw 过程走**票 19 的按需查询接口**。
- **顺带纠正综述记的那个坑**：Claude Code 的"subagent 编辑一般不恢复"在我们这里**不成立**——执行者的事件与 `outputs/` 都在**同一个会话目录**里（票 07），所以 `/undo` 对它一样有效。这是共享一条流换来的直接好处。

### 5. 并发与阻塞（票面第 5 条 + map 的雾）

**`task` 是普通工具调用、在同一个 Turn 内阻塞到执行者结束；同一批里的多个 `task` 可以并发；默认上限 5（goose 的 `GOOSE_MAX_BACKGROUND_TASKS`），可配。**

- **为什么"阻塞"而不是"返回句柄、结果晚到"**：
  - **因果紧**：我能在**同一轮**里说"我让它查了，结果是…，所以我的主张是…"。讨论的价值正在于此；结果晚到就变成票 16 的协议问题（何时入窗、等不等）。
  - 它是普通工具调用 ⇒ 票 02/03 那条"每个 `tool_call` 恰好一条结果"**自动覆盖它**，不需要为"异步结果"发明第二套投递。
  - 票 15 的 `ExecutorSpawned` / `ExecutorFinished` 仍是流上两条独立事件（中间隔着执行者自己的一整段事件），所以**审计与查询的形状不变**。
- **并发从哪来**（本票最技术的一处）：**`task` 自己不碰工作区**——它只是"派发"，所以它的 `effect()` **不是 `WritePaths`、也不是 `Exclusive`** ⇒ 调度器允许同一批里的多个 `task` 并行（票 03 已定 v1 默认整批串行，但**按 `effect` 分流的结构现在就在位**）。
  - **真正的写互斥发生在执行者内部**的 `edit_file` / `bash` 上，用的是**组装期注入的共享 `PathLocks`**——票 03 那句"两个 Executor 是两个 Session 却共享同一工作区，各自一把锁等于没锁"正是为这一刻写的。
  - 这需要一个**语义澄清**：`SideEffect` 判的是"**工作区副作用**"，不是"这次调用是否改变了任何状态"（派发确实改变了会话状态）。→ 交接票 03。
- **上限 5 是成本闸门，不是安全闸门**：写互斥已由锁保证；上限存在的理由是 N 个执行者 × 各自的轮数 × 递增上下文是**乘法增长**，而 Kimi 有 TPD（map 的 Notes）。阈值归票 18。
- **雾里那条"多 agent 的并发边界"因此毕业**：存储层允许交错（票 07）、工具层保证写不互相踩（票 03）、讨论层靠投影规则保证"结论只在完成后入窗"——**所以"讨论继续、执行者在跑"是允许的**，且不会提前泄露结果（那正是票 16 独立首轮要保的多样性）。

### 6. 失败语义（补上 map 雾里"子 agent 失败"那一半）

- 执行者以 `ExecutorFinished { reason: Error | MaxIterations | Aborted | MistakeLimit }` 收尾 ⇒ 那次 `task` 调用得到一条**错误内容的工具结果**（`ok: false` + reason + 它最后说了什么）。
- **讨论不因此中断**：一轮里一个工具调用失败，与其它工具调用失败**同形**（票 03 的 `Result` 路径 + 循环合成）；派发者看到它，可以改派、拆小、或自己上。
- 于是雾里那条只剩"**讨论某轮失败**"那一半（归票 16）。

### 明确不做

- 多 agent 编排 DSL（票面已列）；专职角色 / 第三种身份（第 1 节）；执行者再派执行者（第 3 节）；把执行者过程全量灌进讨论者窗口（第 4 节）；异步句柄式的 `task`（第 5 节）。

### 交接

- **票 03**：① read set 的交接问题有答案了——**不继承、任一方向都不流动**，嵌套 Session 从空开始；② `SideEffect` 需要一个**语义澄清**：它判的是"**工作区副作用**"，所以 `task`（派发）不属于 `WritePaths`/`Exclusive`，多个 `task` 可并发；③ 那份**共享 `PathLocks`** 正是并发执行者的写互斥保障。

- **票 20**：**继承拒绝、不继承允许**有了第二个真实用户（第一个是 plan 模式）；执行者的工具集**不含 `task`**（第 3 节）。

**票 20 交接来的答案（2026-09-13）**：你第 3 条那套继承语义**落成了默认值，不是一条特例规则**。

- **`propagate` 的默认按动作定**：`Deny` 默认 `true`、`Ask` 默认 `true`、**`Allow` 默认 `false`**。所以"继承拒绝、不继承允许"是**默认值的自然结果**，不需要额外约定；用户仍可逐条覆盖。
- **执行者的策略 = 父级传播下来的规则 ∪ 它自己的规则**（你引的 opencode 形状）。
- 你那条硬要求因此**自动满足**："派一个执行者去写"不再是绕过 plan 模式的路径（票 10 的 `Deny` 会传下来）。
- 一条与你有关的边界：**`task`（派发）不属于 `WritePaths`/`Exclusive`**（你那个语义澄清），所以在规则语言里写"所有写类工具都要 `Ask`"时**`task` 不在那一类**——而它派出的执行者内部的写会**各自过门**（用的是你这条继承语义算出来的策略）。这正是"并发执行者"与"权限继承"两件事不冲突的原因。
