# 发言归属与投影接缝

Type: grilling
Status: resolved
Blocked by: 02, 15, 26

## Question

定一条**纯函数**的接缝：

```
project(事件流, 当前说话者, provider 能力) → messages
```

**这是多 agent 讨论里唯一一处"自我/他我"被确定下来的地方。**

**已定的编码规则**（Chart 期定，见 map 的 Notes）：

- **自己的发言 → `assistant`；其他所有人的发言 → `user`**
- **连续的其他发言者要合并成一条 `user` 消息，人名写进正文**（`[architect] …`）
- **`name` 字段只作增强**，不作唯一保障
- 身份（system prompt）**不进流**，永远私有

**为什么"合并 + 正文前缀"是基线而不是回退**：研究核实**两家（Kimi / DeepSeek）对"连续多条同 role 消息"的行为都未文档化**——接受 / 拒绝 / 合并未知。而 Anthropic 是**已文档化**会合并的。所以主动合并既是对未知行为的防御，又顺带让**一份投影跨三家可用**。

**先读** `.scratch/multi-agent-architecture/research/01-debate-conformity-and-speaker-attribution.md` 第 3 节（AutoGen 的做法：内部消息带 `source`，调模型时把其他所有发言者压成 `role="user"` + `name=<source>`，只有自己的输出是 `assistant`；不支持 `name` 的 provider 回退成 `f"{source} said:\n"`）。

要回答：

1. **接线处**：投影住在 provider 适配器里（它知道自己的 role 能力），还是独立一层？**它必须知道 provider 能力表（票 02）和流的形状（票 15）。**
2. **纯函数还是带状态。** 票 07 要求"任何 agent 的 messages 都能从流 + 投影规则**重算出来**"（这是新的不变量）。那投影能不能带预算裁剪状态（票 06 的问题）？如果不能，裁剪必须放在投影之后。
3. **带工具调用的历史怎么投。** 工具调用与结果是 `assistant`/`tool` 配对的。当发言者不是自己时，别人的工具调用历史投成什么？**要不要投？**（可能只需要投结论，不投它的工具往返——那会大幅省 token，但研究说"只暴露结论"无消融证据。）
4. **合并的粒度与顺序**：连续多少条才合并？合并会不会跨轮次边界？（跨轮合并会抹掉"哪一轮说的"这个信号。）
5. **`name` 的字符合法性**：两家文档都写了 `name`，但合法字符集与长度限制本票要核实（若文件里没有，需要补一次 research）。
6. **前缀格式**：`[architect] …` / `architect said:\n…` / 别的？它是"给模型看的"，所以要考虑综述那条原则——**格式要贴近模型在互联网文本里自然见过的样子**。

**票 02 交接来的新约束（2026-09-12）**：`Message::Assistant` 已带 `reasoning_content: Option<String>`，且两家要求回放它（DeepSeek 带 `tools` 时不回传历轮 `reasoning_content` 直接 **400**；Kimi `kimi-k3` / `kimi-k2.7-code` 恒 `keep:"all"`）。所以本票还要回答：**自己的历史思考内容回不回放；别人的（会被投成 `user` 的）思考内容怎么处理**（丢弃 / 并进正文 / 别的）。它与第 3 条「工具历史策略」是同一类问题。

**票 06 交接来的答案（2026-09-12）**：投影**只做归属**，预算裁剪是投影**之后**的另一个纯函数 `trim`（票 06 第 2 节）——所以投影**不带**裁剪状态。另：`AGENTS.md` + skills 一行描述由投影侧前置为**第一条 `user` message**（`Message::System` 身份 → `Message::User` 规则 → 历史），**两段钉住、永不参与裁剪**；且注入内容会以事件形式在流上（票 06 第 5 节）。本票第 2 条的问题已被回答。

**答案要给出：函数签名 + 合并算法 + 前缀格式 + 工具历史策略。** 不要实现。

**票 15 交接来的事实（2026-09-13）**：

- **`speaker_id` 的域**：`Debater(AgentId) | Executor(AgentId) | User | System`，**每条事件必填、无 `Option`**。`System` 收 harness 自身的事件（`SessionStarted` / `SessionEnded` / `HistorySuperseded` / 策略驱动的 `PermissionDecided` / `HookExecuted`）；**`ContextInjected` 挂 `User`**——与你已有的"由投影侧前置为第一条 user message"一致，归属跟着投影走，就不需要特例规则。
- **可见性是投影规则、不是事件字段**：票 15 明确拒绝在事件上放可见性标记。所以"谁能看见什么"由你在 `project` 里算——讨论第 1 轮的互不可见是**时间性**的（A 被调用时 B 的发言还不存在），揭示轮由协议位置决定，执行者的过程按 `SpeakerId::Executor(id)` 过滤。
- **"哪些事件会进模型上下文"是一张写在 `project()` 旁边的穷尽 match 表**（**无 `_` 臂**），不是 payload 上的类型属性——因为 `CONTEXT.md` 已把 `Projection` 判给 provider 适配器侧，放进 `events` 会让 DAG 斜过来。
- **事件的原子单位是完成单元**：`MessageCompleted { role, text, reasoning? }`。日志里**没有**增量文本，所以投影永远不需要处理半截消息——这一条会让你的合并算法简单不少。
- payload 全集见票 15 的 `## Answer` 第 3 节（20 个变体）。

**票 05 交接来的事实（2026-09-13）**——它给你的合并算法加了一条**通用**规则：

- **对每个 `tool_call`，按 `seq` 收集它的所有结果承载事件，拼成一条 tool 消息。** 起因：PostToolUse 的 hook 反馈在流上是独立的 `HookExecuted` 事件（票 15 禁止改写已写事件），而 **provider 只允许一个 `tool_call` 对应一条 tool 消息**——所以合并是**被迫的**，不是风格选项。
- **该规则的可见性**：hook 反馈**跟着它所评注的那条工具结果走**。所以"别人的工具往返投不投"这个问题你一旦回答，反馈的可见性自动跟着同一条规则，**不需要第二条规则**。
- **四条异常路径都会合成一条结果事件**（权限拒绝 / 用户拒绝 / hook 跳过 / `hook.pre` 失败），所以投影**不需要处理"有 `tool_call` 却没有结果"的悬空态**——那个状态只可能在崩溃恢复时出现，归票 07。

**票 10 交接来的事实（2026-09-13）**——多一类要进 `messages` 的注入内容：

- **进入 plan 模式时会注入一条钉住的短指令**（"动手前先读 `PLAN.md`"），它在流上是一条 `ContextInjected` 事件。投影要把它放进 `messages`——**位置规则与 AGENTS.md / skills 同族**（票 06 已定：注入内容由投影侧放置，不是事件自带位置）。
- 它**不是**第一条 user message（那是 AGENTS.md + skills 的位置，票 06 钉死的）；它是**会话中途**注入的，形状上更像票 09 的 skill body（追加在尾部、不破坏前缀缓存）。
- 一条它特有的性质：**它必须"钉住"**（票 10 第 4 节）——即**永不被裁剪**。所以你的"哪些事件进上下文"那张穷尽 match 表旁边，还需要一张**丢弃顺序 / 黏性**的表，而这条指令要落在最黏的一档（比票 09 的"老 skill body"更黏或同档，由你定）。
- 另：`PLAN.md` 的**全文不进上下文**（只在磁盘上，模型要就自己 `read_file`）——投影不需要为它做任何事。

**票 13 交接来的事实（2026-09-13）**——一条**防 bug** 的约定：

- **渲染层的"人看前缀"与你的"模型看前缀"是两套东西，不要共用字符串生成器。** 早期它们很容易长得像（都是 `[名字] …`），但需求不同：你的前缀要**贴近模型在互联网文本里自然见过的样子**（票 17 第 6 条），渲染的要在**每一行**都重复（多 agent 交错时逐行可判）。共用生成器会变成"改一处两边都动"，而其中一边的改动往往是错的。
- 具体差异供你参考：渲染用 `[kimi]` / `[deepseek]` / `[executor:<id>]` / `[user]`、**逐行**；你那边按第 20 行的既定编码（合并 + 正文前缀，`name` 只作增强），**每条合并后的 user 消息一次**。
- 另：渲染的**单位**与你的**单位**恰好一致——两者都按 `tool_call_id` 把工具结果与 hook 反馈归成一件事（票 13 第 3 节）。这不是巧合，是"人对一次工具调用的理解"与"模型对一次工具调用的理解"本来就该同形。

**票 14 交接来的一条过滤规则（2026-09-13）**：

- **`SpeakerId::Executor(id)` 的事件默认不进任何讨论者的投影**——只留结论，而结论**走的是两条别的路**：① 那次 `task` 调用的**工具结果**（对发起者是 `tool` role）；② **发起者自己的发言**（它把结论写进自己的论点）。
  - 所以你的"哪些事件进模型上下文"那张表里，执行者的 `TurnStarted` / `MessageCompleted` / `ToolCall*` / `UsageRecorded` 全部**不进**（对它自己的投影除外——执行者看自己的历史当然要全量，它就是一个正常 Session）。
- **`ExecutorFinished { summary }` 建议也"不进"**：它是审计事件，摘要已经由工具结果交付了。这一条**由你定**，但若你让它进，会和那次工具结果**重复**一次文本。
- 一个由此产生的不对称要记住：**执行者自己的投影是全量的**（它要干活），而**讨论者看它是空的**。所以 `project` 的规则里"当前说话者是谁"决定了同一批事件**双向**不同——这正是你那张穷尽 match 表需要按 `speaker_id` 分支的地方。
- 另：执行者的工具集**不含 `task`**（票 14 第 3 节，深度 1），所以你不会遇到"执行者派执行者"的嵌套投影。

## Answer

**已定（2026-09-13，grilling 两轮 + 一个 research 票）。** 契约来自 Chart 期（自己的发言 → `assistant`、他人 → `user`、合并 + 正文前缀、`name` 只作增强）；纯函数与"裁剪在投影之后"来自票 06；`speaker_id` 的域来自票 15。

**接缝签名（形状）**：`fn project(log: &EventLog, me: &SpeakerId, caps: &ProviderCaps) -> Vec<Message>`

### 1. 接线处（票面第 1 条）

**一份实现，住在 provider 适配器侧，按 `caps` 分叉。**

- 逐字段差异是**数据**不是代码：差异做成能力表上的字段（票 02），投影就是"一张穷尽 match + 几个纯函数"。
- 上游（`agent`）不该知道"Kimi 不接受连续 assistant"这类事——那正是票 02 把差异关进 adapter 的意图。
- 纯函数、**不带裁剪状态**（票 06 第 2 节已定：`trim` 在投影之后），所以票 07 那条"任何 agent 的 messages 都能从流 + 规则重算"成立。
- **"哪些事件进上下文"是一张穷尽 match 表（无 `_` 臂）**，写在 `project()` 旁边（票 15 第 6 节）。

### 2. 别人的回合里投什么（票面第 3 条 + 票 02 的 reasoning 交接）

**三档分开：文本保留；工具调用只留一行摘要；`reasoning_content` 丢弃。**

- **先说清那个硬约束（它决定形状）**：Chart 期已定"别人的发言一律投成 `user`"，所以 **B 的 `tool_calls` 不能以 `assistant` 出现**（否则模型会以为是自己调的）；而一旦把工具往返改写成文本，**与它配对的 `tool` 结果也必须一起改写或丢弃**——否则 provider 的 `tool_call` ↔ `tool` 配对校验会炸（票 02/03 的不变量在**线级**同样成立）。
- **B 的文本 → 保留**（投成 `user` 块、带前缀）。
- **B 的工具调用 → 只留一行摘要**（工具名 + 关键参数的截断），**结果正文不投**。
  - 留摘要保住**可核对性**（A 能看见 B 到底查了什么），代价极小。
  - 丢结果正文：它的价值已经在 B 自己的结论里（B 该引用它）；A 想要原始内容可以**自己读**（它也有 `read_file`）。
  - 与票 14 定下的模式**同构**（过程不进、结论进、raw 按需 zoom）——一条原则管两处。
- **B 的 `reasoning_content` → 丢弃**：① 它是"过程"，与工具往返同类；② **别人的推理被注入 A 的上下文会直接污染 A 的思路**，而讨论的多样性正建立在各自独立推理上；③ **没有任何 provider 要求回放别人的 reasoning**。
- **我自己的 `reasoning_content` → 必须回放**（API 强制）：DeepSeek 带 `tools` 时不回传历轮 `reasoning_content` 直接 **400**；Kimi `kimi-k3` / `kimi-k2.7-code` 恒 `keep:"all"`。所以自己的 `assistant` 消息**逐条带上它**（票 02）。
  - 边界：这是"**我自己的历史 assistant 消息**"的属性，与"他人被投成 `user`"无关——所以丢弃别人的 reasoning 不触发任何 provider 要求。
- 反方诚实说：综述指出"只暴露结论"**没有消融证据**（未测配置）。保留一行摘要就是对它的对冲；而因为这是**投影规则**，将来改成"全投"是局部改动，**不需要预留字段**。

### 3. 我自己的工具往返与 hook 反馈（票 05 交接的通则）

- **对每个 `tool_call`，按 `seq` 收集它的所有结果承载事件，拼成一条 `tool` 消息**（票 05 交接）：`ToolCallCompleted` + 可能存在的 `HookExecuted`（PostToolUse 反馈）都进同一条——因为 **provider 只允许一个 `tool_call` 对应一条 `tool` 消息**，合并是被迫的。
- 顺序：按 `seq` 拼接；工具输出在前、hook 反馈在后，并给反馈加一个**来源标记**，让模型分得清"这是命令输出"与"这是 harness 的评注"。

### 4. 合并的粒度与顺序（票面第 4 条）

**按 role 序列合并，以轮次为硬边界。**

- **判据是 role 序列、不是条数**：从我的视角扫一遍事件流，**连续的非我发言合成一条 `user`**；**没有阈值**（阈值会制造"同样的事有时合并有时不合并"的不确定性，而合并的唯一目的是避开 provider 端"连续同 role"的未知行为——研究已核实两家**都未文档化**）。
- **不跨轮次边界**：`RoundStarted` 是硬边界（跨轮合并会抹掉"哪一轮说的"这个信号）；**轮次写进正文前缀**，所以断开不丢信息、也不需要额外的分节消息。
- **两条钉住的例外**：① **第一条 `user`（AGENTS.md + skill 清单）不参与合并**——票 06 要它逐轮不变，把它卷进一个会变的块里会让前缀缓存失效；② **`ContextInjected`（如 plan 模式那条指令）独立成条**，否则它就不再"钉住"了。
- **顺序严格按 `seq`**；块内按 seq 拼接、每段带前缀。

### 5. 前缀格式（票面第 6 条）

**`[轮 N · 名字] …`，只加在别人的发言上。**

- 用紧凑行首标签而不是 `名字 said:\n`：① 综述那条原则是"格式要贴近模型在互联网文本里自然见过的样子"，`[…]` 是聊天记录/日志里极常见的形状；② `said:` 每次发言多占一整行；③ 它还与票 13 给**人看**的逐行前缀长得像（票 13 已明确**两者不共用生成器**）。
- **对自己不加前缀**：自己是 `assistant`，不需要自我标注；而且给自己的历史 assistant 消息加前缀会**污染回放**（那是我自己要续写的内容）。
- **`name` 字段：发，但只发在 `user` / `assistant` 上，且值消毒到 `[A-Za-z0-9_-]`、保持短。** 三条具体规则（依据票 26 的产物 `research/07-message-name-field.md`）：
  1. **`tool` 消息不发 `name`**。事实依据：**DeepSeek 的 tool 消息 schema 里没有这个字段**（字段只有 `role` / `content` / `tool_call_id`，EN+CN 双证），OpenAI 的 `ChatCompletionToolMessageParam` 同样没有；Kimi 只是因为四个 role **共用一个 `Message` schema** 才"语法上允许"，且没有 tool+name 的语义或示例。⚠️ **这是对 `research/02` §4.2 的纠正**——它那句"DeepSeek 四个变体都带 `name`"是错的。
  2. **值消毒到 `[A-Za-z0-9_-]` 并保持短**：不是因为某家文档要求，而是因为**三家（Kimi / DeepSeek / OpenAI）都完全没有写字符集与长度**（只有 `type: string` + 那句 "optional name for the participant"）——所以在"**没有任何文档背书**"的前提下，只发"任何合理实现都必然接受"的形状。我们的说话人名构造上就很短（`kimi` / `deepseek` / `executor-<短 id>`）。
  3. **绝不依赖它**（Chart 期已定："只作增强、不作唯一保障"）：正文前缀是基线，所以 `name` 被忽略、被截断、乃至某家对它做了别的处理，**归属信息都不丢**。
- 一条**不必担心**的事：`name` 唯一被文档化的"重语义"是 Kimi 的 **Partial Mode**（它是 output prefix 的一部分、"compelling it to output content in the voice of the specified character"）——**我们不用 partial**，而普通 chat 下三家都没有文档化的行为副作用（只有那句信息性的 "differentiate participants"）。没有任何一家把它标成 deprecated。

### 6. 可见性与黏性（票 10 / 14 交接）

- **执行者的事件不进讨论者的投影**（票 14 第 4 节）：`SpeakerId::Executor(id)` 的 `TurnStarted` / `MessageCompleted` / `ToolCall*` / `UsageRecorded` 全部滤掉；**`ExecutorFinished` 也不进**（它是审计事件，摘要已由那次 `task` 的工具结果交付——再进就是同一段文本出现两遍）。
  - 不对称要记住：**执行者自己的投影是全量的**（它要干活），讨论者看它是空的——所以同一批事件**双向不同**，`project` 的 match 表必须按 `speaker_id` 分支。
- **plan 模式那条注入（`ContextInjected`）与钉住的第一条 `user` 同档：永不参与裁剪**（票 10 第 4 节的推理全部依据"这个指针不会消失"）。多次切换模式用**幂等注入**消掉重复。
- 于是**丢弃顺序**（细化票 06 第 3 节）变成：
  **老普通工具结果 → 老 skill body → 老整轮 → 该 Turn 硬失败**

- **钉住的注入永不参与裁剪、不在这个序列里**。理由：**票 09 明说 skill body 比普通工具结果更黏**，所以工具结果必须先丢。

### 明确不做

- 把别人的工具结果正文投进上下文；回放别人的 `reasoning_content`；只靠 `name`、正文不加前缀；跨轮合并；为"工具历史策略"预留配置字段（它是纯函数规则，改它是局部改动）。
