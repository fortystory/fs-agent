# 权限表达与沿委派链的继承

Type: grilling
Status: resolved
Blocked by: 05, 14

## Question

**本票是从旧图「极简型」砍掉项里重开的**。旧图砍掉它的原文理由是："**三档模式 + 危险命令黑名单覆盖自用需求**"，砍掉的是**权限分类器模型、完整 allow-deny DSL、声明式策略文件**。

多 agent 让这条理由失效，因为**委派引入了"继承"这个新语义**，而继承是**规则的集合运算**：

> **opencode 的答案**：子 agent **只继承父级的 `deny` 规则和 `external_directory`**，而 `todowrite` 与 `task` **默认强制拒绝**，除非子 agent 自己的规则集里显式提到；`subagent_depth` 默认 **1**。综述的评价：**「继承拒绝、不继承允许」，且递归深度默认 1**。

**三档模式 + 黑名单表达不了"哪些规则向下传播、哪些不传播"。**

要回答：

1. **权限的最小表达形式。** 不需要完整的声明式 DSL，但需要能表达：规则的**主体**（哪个 agent）、**作用域**（工具 / 命令前缀 / 路径）、**动作**（allow / ask / deny）、以及**传播性**（是否向子 agent 继承）。最小可用是什么形状？
2. **优先级语义。** 综述记录 Claude Code 是 `deny > ask > allow`，且**忽略具体程度**（一条宽泛的 deny 压过一条精确的 allow）；opencode 是 **last-match-wins**；Amp 是 **first-match-wins**。要选一种并说清理由——**这三家是三种不同的语义，选错了规则会互相打架。**
3. **deny 的强度**：Claude Code 里 `deny` 写一个裸工具名会**把该工具从上下文里移除**，而不只是拦调用。跟不跟？
4. **protected / critical path 断路器。** 综述标 🔷「极低成本、极高收益」：`.git`、shell rc、`.npmrc` 等敏感路径的写入永不自动批准；`rm` 打到文件系统根 / 家目录时**连 allow 规则和 hook 的 "allow" 都不能批准**。注意实现顺序：安全检查在 allow 规则**之前**跑。要不要进 v1？
5. **动态注册工具的标记不可信**（与票 11 直接交界）。票 03 把"内建工具的副作用标记可信、动态工具的如何被信任"交接给了票 11——但**执行那条信任策略的地方是本票的权限门**。两票的接口要在这里对齐：票 11 定策略，本票定它落在权限判定的哪一步。
6. **`.env` 等敏感文件的默认姿态。** 综述指出 opencode 文档写 `*.env` deny、`*.env.example` allow，**但其代码实际兜底是 `ask` 而不是 `deny`（文档与实现不一致）**——自研时照 `deny` 做更安全。注意你的配置**不**读项目 `.env`（map 的 Notes），但 agent 读文件时仍会碰到它。
7. **这是"减少误伤"还是"抵抗攻击"。** 综述把三条诚实声明合起来给出结论：**命令黑名单的价值是"减少误伤"，不是"抵抗攻击"，也不该被当成主要防线**（Amp 更直接地说静态检查 "gives you a false sense of security"，因为模型会"write throwaway scripts"）。这个定位要写进本票答案，避免后来者高估它。
8. 明确**不做**：独立分类器模型做权限判定（另一次 LLM 调用 + 一套策略提示，属产品级投入）。

**票 05 交接来的事实（2026-09-13）**——它把你要解决的问题的**边界**钉住了：

- **门的输出是封闭三态** `Allow | Ask | Deny`（+ `why`），且"hook 只能收紧"要求这个格是**全序**。所以**不要动裁决类型**；你要打开的是**门的输入侧**：模式（`readonly` / `ask` / `auto`）、危险命令黑名单、cwd 路径限制、**规则表达式**，以及**沿委派链的继承**。你第 1 条要的"最小表达形式"因此是**策略语言**的最小形式，不是裁决类型的最小形式。
- **门的接口是纯函数** `Policy → Verdict`：不读环境、不与人交互、**不追加事件**。所有交互（询问）由 `agent` 循环在门外做——所以你的规则语言不需要为"询问"设计回调/副作用。

- **"继承拒绝、不继承允许"在机制上可行**（你第 1 条引的 opencode 答案）：拒绝是一个**约束**，而约束能沿链传播且只可能变严——与"hook 只能收紧"是同一个代数。

**票 10 交接来的第一个真实用例（2026-09-13）**——你的规则语言必须能表达它，否则"硬 plan 模式"落不了地：

- **要表达的东西**：`非 ReadOnly 的调用 → Deny`，**外加一条路径豁免**（`WritePaths` 的**全部**路径都是 `<repo>/PLAN.md` → `Allow`）。

  - `Exclusive`（`bash`）**不可豁免**——它没有路径集合。
- **要表达的传播性**：**`Deny` 必须能沿委派链继承**。plan 模式的安全完全押在这上面——不继承的话，"派一个执行者去写"就是绕过它的最短路径。这正是你第 1 条要的"传播性"字段的**第一个非假想用户**。

- 另一个边界：**`Ask` 与 `Deny` 在这条用例里必须可区分**——plan 模式要求 `Deny`（硬），不能退化成 `Ask`（每次都问），所以你的规则语言不能把两者折叠成一个"不放行"。

**票 11 交接来的用例与一个可选接口（2026-09-13）**：

**票 13 交接来的一个边界（2026-09-13）**——它可能改变你的一条规则的位置：

## Answer

**已定（2026-09-13，grilling 两轮）。** 门的形状来自票 05（纯函数、封闭三态、hook 只能收紧）；委派链来自票 14；动态工具的交接来自票 11。

### 0. 一个必须先解决的冲突（准备时发现的）

票面第 2 条要选优先级语义，而 **Claude Code 那条（`deny > ask > allow` 且忽略具体程度）会让票 10 的 `PLAN.md` 豁免失效**——票 10 的形状是"一条宽泛的 deny + 一条窄 allow"，而"忽略具体程度"意味着宽泛的 deny 压过精确的 allow。

**解决方式不是放弃这条语义，而是把"豁免"从"一条竞争的规则"改成"deny 条件里的一个与项"**（第 1 节）。它也顺带确定了规则的形状：**规则匹配的是"这次调用的谓词"，不是"工具名"**。

### 1. 规则的最小形状与优先级（票面第 1、2 条）

**一条规则 = 谓词 + 动作 + 传播性；策略是一个规则集合；解析语义 = `deny > ask > allow`，忽略具体程度。**

```
Rule {
  subject:   Any | Debater | Executor | Agent(id),   // 主体
  scope:     Scope,                                   // 对这次调用的谓词
  action:    Allow | Ask | Deny,                      // 与门的裁决同一套三态（票 05）
  propagate: bool,                                    // 默认按动作定（第 3 节）
}

Scope = Tool(glob)              // "edit_file"、"custom__*"（票 11 的 `__` 谓词直接可用）
      | CommandPrefix(argv)     // bash 的 argv 前缀（票 11 说这是命令前缀的真实用武之地）
      | Path(pattern)           // 路径匹配（前缀 / 通配）
      | PathSet(exact)          // **路径集合恰好等于**（票 10 的硬约束）
      | All                     // 兜底（例如"非 ReadOnly 一律"）
```

- **为什么"作用域"是谓词而不是名字匹配器**：`effect(&self, args)` 本来就是从 args 算出来的（票 03），所以"看 args 决定匹不匹配"是**既有的形状**；而它让"非只读 **且** 写入集 ≠ `{PLAN.md}`"这类条件**可以直接写**，不需要靠优先级去打架。
- **`PathSet(exact)` 不是可选加强**：票 10 明说"豁免的形状必须是**全部路径都是它**，否则一个同时写 `PLAN.md` 与 `src/main.rs` 的调用能借道"。只有 `Path(pattern)` 的话，那个豁免写不出安全的形状。
- **为什么忽略具体程度**：选 `deny > ask > allow` 让**规则优先级、hook 的收紧（票 05）、执行者的继承（票 14）共用同一个代数**——都在 `Allow < Ask < Deny` 上取上确界，**只有一套合并语义**。而"具体程度优先"需要一个定义（工具名 vs argv 前缀 vs 路径，谁更具体？），Claude Code 明确忽略它，很可能就是因为定义不清。
- **保守方向也对**：冲突时倒向 `Deny`，而本票第 7 条自己说这套东西的价值是"**减少误伤**"而不是"抵抗攻击"。
- **代价诚实说**：它**不能表达"除了这一个例外"**——所以例外必须写进 deny 自己（第 0 节）。这是这条语义的唯一真实约束。

### 1b. 四个内置模式（审计发现：它们被五个票使用、却从未被定义）

票 05 把"模式"当成门的**输入**交给本票，而本票的答案只给了规则语言——于是 `readonly` / `ask` / `auto` 在全图被使用而没有定义。补上（`plan` 由票 10 定，一并列出以成一个完整集合）：

| 模式 | 判据 | 备注 |
|---|---|---|
| `readonly` | 非 `ReadOnly` 的调用 → **`Deny`** | **没有任何写豁免**。"只读"是一个硬的立场，要放行就切模式——与票 10 对 plan 选 `Deny` 而非 `Ask` 是同一条理由 |
| `ask` | 写类（`WritePaths` / `Exclusive`）→ **`Ask`**；只读 → `Allow` | 这是 opencode 的 plan 形状，也是"默认安全又不打断"的那一档 |
| `auto` | 默认 **`Allow`** | **只受规则与断路器约束**——它**不是**"跳过权限"：票 21 的 root 防呆、断路器、`.env` deny 照样生效 |
| `plan` | 非 `ReadOnly` → `Deny`，**唯一豁免**：`WritePaths` 的**全部**路径 = `<repo>/PLAN.md` → `Allow` | 与 `readonly` 的差别**只有那一条豁免**（票 10） |

- **四条对每个模式都成立**：① 断路器**短路在规则之前**，任何模式都翻不动（第 4 节）；② hook 只能收紧（票 05）；③ 沿委派链传播的是 `Deny` / `Ask`（第 3 节）；④ 无交互渲染器时 `Ask → Deny`（第 6 节）。
- **模式是 Session 的策略值、不进流**（票 10 第 6 节）；`--continue` 回到 `config.toml` 里的值。

### 2. 评估次序（把三处交接对齐）

```
① 断路器（短路 Deny，早于一切）               ← 第 4 节，票 05 的次序
② 规则集合求值 → 取上确界（deny > ask > allow） ← 第 1 节
③ hook 的收紧（只能更严）                      ← 票 05
④ 生效裁决 = 上确界(②, ③)
⑤ 无交互渲染器时 Ask → Deny（循环做）           ← 第 6 节
```

- **断路器最外**：票 05 已定"安全检查在 allow 规则**之前**跑"，落在这里就是**短路返回**。
- **hook 在规则之后**：它可以收紧一个 `Allow`，但**不能放松一个 `Deny`**（票 05 的代数保证）。
- **`Ask` 的降级在最外**：它是运行期事实，不是策略（第 6 节）。

### 3. 传播性："继承拒绝、不继承允许"是**默认值**，不是特例规则（票面第 1 条的后半）

- **`propagate` 的默认按动作定**：`Deny` 默认 `true`、`Allow` 默认 `false`、`Ask` 默认 `true`（询问也是一个约束——子 agent 不该绕过父级的"要问一下"）。
- 所以"继承拒绝、不继承允许"**不需要一条特例规则**，它是**默认值的自然结果**；用户仍可逐条覆盖。
- **执行者的策略 = 父级传播下来的规则 ∪ 它自己的规则**（opencode 的形状）。
- **两个真实用户**（票 14 交接）：plan 模式的 `Deny`（票 10）与执行者的权限继承（票 14）。**票 10 那条硬要求因此自动满足**："派一个执行者去写"不再是绕过 plan 模式的路径。

### 4. 断路器：进 v1，且它是"断路器"不是"规则"（票面第 4 条）

**短路返回 `Deny`，早于规则求值**——所以**任何 allow 规则都翻不动它**；而 hook 只能收紧，所以"连 hook 的 allow 也不能批准"也自动成立。

v1 两条：

1. **敏感路径的写入永不自动批准**：`.git/`、shell rc（`.bashrc` / `.zshrc` / …）、`.npmrc`、`.ssh/`。**建议 `.git/` 与 `.ssh/` 直接 `Deny`**，其余至少 `Ask`。
2. **`rm` 打到文件系统根 / 家目录**：argv 首元素是 `rm` 且任一参数解析后是 `/`、`~`、或它们的父级（`/` 没有父级，就是它自己）⇒ `Deny`。**这是最不可逆的一类，也是唯一"任何规则都不能放行"的一类。**

**诚实定位（票面第 7 条）**：**命令黑名单的价值是"减少误伤"，不是"抵抗攻击"，也不该被当成主要防线。** 静态检查会给人**虚假的安全感**（Amp 的原话）——模型会写一次性脚本绕过它。真正的纵深是：**写串行化（票 03）+ 权限门 + 断路器 + 秘密打码与会话文件的可见性（票 21）**。别高估这一层。

### 5. `.env` 家族的默认姿态（票面第 6 条）

**`deny` 整个 `.env` 家族**（`*.example` / `*.sample` / `*.template` 除外）。

- 事实：opencode 的**文档写 `*.env` deny、`*.env.example` allow**，但**代码兜底是 `ask`**——不一致时**取更安全的一边**。
- 这类文件的**全部内容就是凭据**，没有"读一下也没事"的场景。
- **票 21 那条泄露面**：读进来就会**永久留在会话文件与 `outputs/` 里**。
- 注意：我们的**配置**不读项目 `.env`（map 的 Notes），但 **agent 的文件工具会碰到它**——所以这条规则是有用的。

### 6. 两处落点

- **headless 的 `Ask → Deny` 降级：循环在门外做**（维持票 13 的默认）。理由：**"有没有交互能力"是运行期事实**（取决于启动时选了哪个渲染器），不是关于工具 / 路径的策略；把它塞进门会让门的输入多一份状态，而门是**纯函数、不读环境**（票 05）。门的裁决如实保持 `Ask`，降级在门外，**理由进 `PermissionDecided.why`**（票 19 要求那个字段始终填）。
- **用户答"总是允许"时，只改会话内的策略，不写用户的 `config.toml`。**
  - 自动写用户的配置文件是**改变用户资产的副作用**——而本图的纪律是**工具绝不擅自改用户的文件**（票 10 对 `PLAN.md` 立的就是这条）。自用工具里"加一条规则"该由用户自己编辑 config：看得见、能 review、能提交。
  - 但**会话内记忆要有**（否则同一个文件每次写都要问）：往当前 Session 的策略里追加一条 `Allow`（`subject = 当前 agent`）。
  - **它不进流**——与票 10 对模式的立场一致：**策略是 Session 的值，不是流的内容**。所以 `--continue` 后它会消失（要持久就自己写 config）。

### 7. 动态工具的信任策略落在哪（票面第 5 条）

**门这一侧没有额外的信任策略要落。**

- 票 11 已经把"动态工具的标记可不可信"这个问题**取消**了：它的声明语法里没有副作用类别这个字段，`effect()` 恒为 `Exclusive`。所以**没有一条"不信任动态工具"的特例规则**。
- 自定义工具是权限规则的**普通目标**，按声明名匹配（`custom__<ns>__<tool>`）；而名字里的 `__` 是**词法可判定的谓词**（内建名永不含 `__`），所以 `Scope::Tool("custom__*")` 一条规则就兜住"我新加了个自定义工具、忘了配规则"这个真实事故。
- 一条来自票 11/14 的边界：**`task`（派发）不属于 `WritePaths` / `Exclusive`**（它自己不碰工作区）——所以如果你写"所有写类工具都要 `Ask`"，`task` 不在那一类里；而它派出的执行者内部的写会各自过门。

### 8. deny 的强度：不跟 Claude Code 的"从上下文移除"（票面第 3 条）

**拒绝只拦调用；工具始终留在 `tools` 数组里。** 需要"工具不存在"，就在**组装期不注册**它（票 14 对执行者的 `task` 就是这么做的）。

- **缓存**：`tools` 数组是请求**前缀**的一部分，中途移除会废掉前缀缓存（票 18 刚把这条钉死）。
- **更早更硬**：组装期不注册是"工具不存在"，比"存在但被拒"更彻底。
- **拒绝本身就在教模型**：一条错误内容的工具结果（票 03/05 的不变量）已经足够让它别再试。

### 明确不做

- 独立分类器模型做权限判定（票面第 8 条）；完整 allow-deny DSL；声明式策略文件（旧图砍的——本票的"规则集合"就是它的**最小可用替代**，而不是它的复活）。
- 优先级用"具体程度"或 last-match-wins（第 1 节）；deny 时从上下文移除工具（第 8 节）；把渲染模式当策略输入（第 6 节）；写回用户 `config.toml`（第 6 节）。
