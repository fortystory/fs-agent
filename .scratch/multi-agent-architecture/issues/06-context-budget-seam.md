## Answer

**已定（2026-09-12，grilling 与用户逐轮确认）。输入事实：`docs/research/coding-agent-features.md` 第 3、4 节；票 02 的能力表。**

### 0. 两条贯穿全票的区分

- **窗口预算 ≠ 会话累计**：前者是物理约束（超了就是 400），后者是速率/成本闸门。两者分开算、分开拥有。
- **预算不是状态，是函数**：本票定下的每一个量都能从（日志, 能力表, 规则）重算 → **多 agent 并发下窗口层不需要任何锁**。

### 1. 预算公式住在 `context`（票面第 1 条）

```
usable_input(agent) = caps.context_window − min(20_000, caps.max_output_tokens)
```

- 公式照抄 opencode（综述：手写魔法数字阈值换模型就失效），**住在 `context`**；输入取自票 02 的能力表。**不住 provider**——provider 只报告事实（窗口多大、输出上限多少），`context` 决定留多少给输出。票 01 的 DAG `context → provider` 正是为这条准备的。
- **按 agent 各自的模型算**：两个讨论者是两份 caps → 两个不同预算。**"全局预算"在窗口这一层不存在。**
- **要分清的细节**：能力表的 `max_output_tokens` 是**模型上限**，与**本次请求设多少 `max_completion_tokens`** 是两件事。后者在 Kimi 侧会被网关用来**预估**是否触顶（K-intro：按 `max_completion_tokens` 算限流、"regardless of the actual number of Tokens generated"）——**设得过大是提前撞限流**。那条归票 18；预算公式不得把它们混为一谈。

### 2. 裁剪在投影之后，两者都是纯函数（票面第 2 条）

```
messages(agent) = trim( project(log, speaker, caps), usable_input(caps), policy )
```

- `project`（`provider::projection`，票 02 已定）**只做归属**：自己 `assistant`、别人 `user`、合并加前缀（细节归票 17）。
- `trim`（在 `context`）**只做预算策略**；`context → provider` 让它可以拿到 `Message` 类型与能力表。
- **两者都是纯函数 → 票 07 的不变量（"任何 agent 的 messages 都能从流 + 规则重算"）成立。**（票 07 把措辞精确成 **`流 + 落盘文件 + 投影规则 → messages`**，见本文件末尾的交接块）
- 反例：把预算塞进投影 → 投影同时承担"自我/他我编码"与"预算策略"，票 17 变胖且无法单独调预算；裁剪带状态（记住丢了什么）→ 不变量当场破裂。

### 3. 两个机制的边界与状态归属（票面第 3 条）

它们**不在同一时刻、也不在同一批数据上**：

| | 单次结果截断 | 超预算丢弃 |
|---|---|---|
| 何时 | **入流之前**（工具完成时由 `agent` 调 `context` 的截断函数） | **每次投影之后的 `trim` 里** |
| 作用 | 内容级：超上限 → **全文落盘**，事件里只放**预览 + 落盘指针** | 视图级：**只读**，日志一条不删，只是这次发出的 messages 少几条 |
| 上限 | 可配，默认按估 token **25_000**（Anthropic 文档的默认值），超限给 head/tail 预览 | `usable_input(caps)`（第 1 节） |

**丢弃顺序**：先丢**最老的工具结果**（综述：20 行代码覆盖 90% 长任务）→ 仍不够丢**最老的整轮** → 仍不够则**该 Turn 硬失败**。那个硬失败就是"真爆窗"的信号，也是将来 compaction 的触发点。

**细化（票 09 第 4 节，2026-09-12）**：在这个顺序里**插入一类**，最终为 **老工具结果 → 老 skill body（超出 25k 总上限的最老先丢）→ 老整轮 → 硬失败**。skill body 比普通工具结果更黏（模型正照着它做事）。

**状态归属**：**"当前预算"这个状态不存在**。`usable_input(caps)` 与 `trim(messages, budget)` 都是纯函数。→ 多 agent 并发下窗口层**不需要加锁**；唯一需要锁的仍是 `EventLog` 的追加（票 01）。（**以票 15 为准**：单一写入者独占文件句柄，不需要锁）。

### 4. 会话累计与 TPD（票面第 4 条）

- **窗口预算**：物理约束，每 agent 按各自模型算（第 1 节）。
- **会话累计**：**从 `EventLog` 上的 `Usage` 事件求和得来的派生值**——票 02 已把两家 usage 归一成 `Usage`，现成可用。**不是隐藏状态**（与票 02 的 `pending` 同一原则）。
- **TPD 不折进窗口预算**：它是"当天不可用"的速率/成本闸门，归 **票 18**。本票的职责是把**数据**备好（归一化 `Usage` + 可重算的会话级累计），让票 18 站在一个可查的计数器上做硬停。

### 5. `AGENTS.md` / skills 的注入位置（票面第 5 条）

- 每次调用由投影侧统一前置为**第一条 `user` message**，布局：`Message::System`（本 agent 的身份）→ `Message::User`（AGENTS.md + skills 一行描述）→ 投影出的历史。**不要拼进 system prompt**（综述结论表：放第一条 user message 是为了保住缓存前缀，第 11 节称其为"免费的 5~10 倍成本差"）。
- **前两段在最前面且逐轮不变** → 前缀缓存才可能命中（票 02：Kimi 缓存门槛是上一条请求 >256 prompt tokens 且前缀完整匹配）。
- **必须钉住（pin），永不参与第 2 节的 `trim`。** skills 的一行描述挂在同一条（细节归票 09）。
- **注入内容记成流上的一条事件**（类型由票 15 定），使 `project` 真的是"流 + 规则"的函数——否则 AGENTS.md 改一次、重算结果就变。**私有 system prompt 仍不进流**（它是配置 + 名册身份的确定性函数）。

### 6. v1 的朴素边界与返工判断（票面第 6 条）

- v1 = **字符数/4 估 token** + 第 1 节公式 + 第 3 节丢弃顺序；**自动 compaction（~90% 阈值）后置**，触发点就是第 3 节那个"丢完仍不够"的硬失败。
- **不会返工——但有两个今天必须做对的前提**：
  1. `trim` 是**独立的纯函数**（第 2 节）→ compaction 只是**换一个 trim 策略**，投影、循环、工具层都不动。
  2. 将来 compaction 产出的**摘要必须记成流上的一条事件**（与第 5 节同一条原则）。摘要是一次模型调用的产物；留在流外，`trim` 就不再是"流 + 规则"的函数，不变量破裂、重放对不上。
- 反过来：若把裁剪塞进投影、或把摘要留在流外，compaction 到来时**必须返工**。这是今天把这两条钉死的理由。

### 7. 明确不做（票面第 7 条 + 相邻）

- **repo map 的图排序** → 票 12；**向量检索 / RAG** 不在范围内（综述：代表性实现里没有以它为核心卖点的）。
- **自动 compaction 本身** → v1 后置；**`@file` 引用展开**、**`.gitignore` 感知** → 后置项。
- **AGENTS.md 的向上/向下层级查找** → 票 09 与 `/to-spec` 的范围（本票只定注入**位置**与**钉住**）。

**票 07 交接来的答案（2026-09-13）**：你在第 99–102 行交给票 07 的两件事都关了。

- **落盘指针的路径与形态**：落在**会话目录内**——`~/.local/share/fs-agent/sessions/<cwd-slug>/<session-id>/outputs/<tool_call_id>.txt`。文件名用 **`tool_call_id`** 而不是 `seq`，因为你的规则是"**单次结果截断在入流前**"，而 `seq` 由 writer 在**追加时**才分配（票 15 的"单一写入者"）——落盘早于取号。生命周期与会话一致（**删会话 = 删目录**），**v1 不自动清理**。
- **指针失效**：**降级为预览、绝不失败**——因为你已经保证事件里带预览，所以截断后的**消息级** trajectory 仍可从流重建；指针只是保真度加成。失效时报**一次**诊断，不是每条报一次。
- **你那条"这等于把『流是唯一真相源』变成『流 + 落盘文件』"被正面确认**：票 07 把不变量的措辞正式改成了 **`流 + 落盘文件 + 投影规则 → messages`**，并同时钉死**投影不读落盘文件**（否则你的 `trim` 与票 17 的 `project` 都不再是纯函数）。模型要全文自己 `read_file` 那个路径，**不需要新工具**。

**票 21 交接来的一步（2026-09-13）**：你那个"**入流前**"的处理点现在是一条**三步流水线**：

> **打码 → 截断 → 落盘**

- **打码必须在最前**（票 21 第 3 节）：它是**值级、best-effort** 的替换（`sk-…` / `AKIA…` / `ghp_…` / 私钥块 / `Authorization: Bearer …` → `[REDACTED:<kind>]`）。
- **为什么必须在入流前**：票 19 的查询接口**直接读会话文件**（顺序读、不建索引）——所以打码若发生得晚（例如只在渲染时），查询接口会**绕过它**。
- **一个干净的性质**：因为打码在**事件追加之前**，所以**流上的文本 == 模型当时看到的文本**（一致）；而**工具执行时用的是真值**——那是唯一的分歧。
- **范围不只工具结果**：**消息正文也要过**（票 21 第 3 节）——因为泄露面是**磁盘**，而"某个 agent 在自己的发言里复述了密钥"正是跨 agent 那条路径的唯一剩余形态。
- **唯一例外：`outputs/<tool_call_id>.before` 不打码**——它是 `/undo` 的字节级还原源（票 21 第 3 节）。
