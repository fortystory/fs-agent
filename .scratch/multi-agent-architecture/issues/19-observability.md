### 2. 查询接口：CLI 子命令族，四个动词，不建索引

- `sessions ls` —— 列出会话（id / cwd / 起止 / 轮数 / token / 缓存命中率）
- `sessions show <id> [--round N] [--speaker X] [--kind K] [--tool T] [--only-error]` —— 过滤后的时间线
- `sessions replay <id> --speaker X --round N` —— **投影重算**：那个 agent 在那一刻看到的**确切 `messages`**（票 17 的机制；调试投影 bug 的唯一手段）
- `sessions stats <id>` —— 聚合计数（第 4 节）

**不建索引**：`seq` 就是行号、会话文件是顺序写的、量级是几千到几万行——一次顺序读 + 内存过滤就够。**索引会是第二个真相源**（要自己的写入者与失效纪律），而票 07 的不变量是"流是唯一 trajectory"。

**输出**：默认给人看的表格，`--json` 可管道化；**stdout 只放结果、诊断走 stderr**（与票 13 对 headless 的纪律同一条）。

**这是给人用的，不是给 agent 的新工具**：agent 要看自己的历史，它已经有投影了（票 17）；把会话目录挂进它的工具面是**权限问题**（交接票 20），而"会话文件里有什么"是**泄露面**（交接票 21）。

### 3. 事后时间线的两个视图（票面开头那句话）

- **默认视图：按轮次分组的时间线。** 每轮一节，节内按 `seq` 排，每条带说话人（与票 13 的 live 前缀**同形**：`[轮 2 · kimi]`）+ 事件种类的短标签；**工具调用与其结果归成一条**（与票 13/17 的归并单位一致），hook 反馈与诊断作为缩进的附加行。
- **`--files` 视图：按文件索引的改动史。** 文件 → 时间线（轮次 / 说话人 / 哪个工具调用 / 成功或失败）。它是**唯一一个按"工作区对象"而不是按"时间"索引的视图**，而"谁改了我的文件"正是人最常问、也最难从时间线里 grep 出来的那件事。它是**推导**出来的（从流上的 `ToolCallStarted` + 参数里的路径），**不是新字段**。（本视图**只含 agent 的改动**——用户手势如 `/undo` 的写回、`/plan` 的"覆盖"清空**不进流**，见票 07 第 7 节）。
- **不做**交互式浏览器（票面明确不做）：视图是**一次性输出**，不是可导航的 UI。

### 4. 诊断指标：内置一组固定指标 + 保留原语（票面第 4 条）

**指标 = 流上的聚合查询，不是新埋点**（票 15"结构化日志免费"的直接推论）——实现上它就是一组 group-by，没有独立的埋点通道。

**内置的固定指标**（`stats`）：

- **每个 agent 的 token / 花费 / 缓存命中率**——"哪里白花钱了"。
- **每轮的调用数与轮次分布**——一次讨论只有 3 或 5 次调用（票 16），所以这个量是**离散可枚举**的。
- **单侧缺席率** ⚠️——票 16 点名：**缺席会被读成共识**，这是最危险的静默误读，必须主动报出来。
- **执行者失败原因分布**（`Error` / `MaxIterations` / `Aborted` / `MistakeLimit`）——"我给的 brief 是不是太宽 / 太窄"。
- **编辑匹配梯的命中级别分布** ⚠️——票 04 点名：**降级成功是静默的**，不主动统计就永远发现不了"这个模型总在踩缩进"。
- **`read-before-edit` 拒绝次数与 read set 失效次数**——"模型在凭想象改文件"的直接信号。
- **权限决策分布**（`decision` × `source`）——"我的权限策略是不是太烦了"。
- **hook 三类结果分布**（放行 / 收紧 / 失败）。
- **讨论的分歧率与停法分布**（四个 `RoundEnded` 原因）。

**为什么固定指标值得内置**：它**替你问了该问的问题**——上面标 ⚠️ 的两类恰恰是**静默**的（不报错、只默默发生），而你不会想到去查一个你不知道存在的问题。

**但不许固定指标成为唯一入口**：`show` 的过滤原语（round / speaker / kind / tool）是逃生口，否则遇到新问题就得改代码；**原语 + `--json`** 保证任何新问题都能被组合出来。

### 5. 编辑匹配那类诊断量落在哪（票 03/04 交接，票 15 留的缺口）

**不加新事件变体；它们以"约定文本"落在既有 payload 里，而渲染与解析共享同一个格式定义。**

- **事实基础**：票 04 已经定了"级名**进工具结果** → 可观测"（它的 `Matcher::name()`）；票 03 已经定了 `read-before-edit` 的拒绝产物是**一条错误内容的工具结果**。所以**这两类信息本来就已经在流上了**——缺的只是"可机器读"。
- **共享格式定义是这个方案的可靠性来源**：渲染那段文本的地方与解析它的地方**用同一个常量 / 模板**，所以它们不可能漂移（漂移是文本方案唯一的真实风险）。
- **为什么不给 payload 加通用 `diagnostics` 口袋**：那正是本图反复拒绝的**预留字段**（与票 04 拒绝 `edit_format` 同一条），而且它会鼓励把越来越多东西塞进去。
- **为什么不加一类诊断事件**：为一个诊断量去动那个**刚定死、三层循环共用**的枚举，代价大于收益；而且每次编辑多一条事件会让流变大。
- **一条判据留给将来**：若某个诊断量从"诊断"升级为"**权威**"（有东西按它做决定，而不只是给人看），那就该给它结构化的位置——那时再动枚举。

### 明确不做

- OTel 导出、trajectory 浏览器、多前端订阅的完整 event-sourcing 架构（票面第 7 条）。
- 索引库 / 索引文件（第 2 节）；新的埋点通道（第 4 节）；为诊断量加事件变体（第 5 节）。

- **票 13**：事后视图的说话人前缀与你的 live 前缀**同形但独立实现**（票 17 已定"人看的前缀"与"模型看的前缀"不共用生成器；这里再加一条：**live 与事后**也不必共用生成器，但**格式定义可以共享**）。
- **票 20**：agent 能不能读**自己的 transcript**（会话目录在工作区之外）是一个权限问题，本票不替它决定；但要注意"给它读"等于把一份完整 transcript 挂进它的工具面。
- **票 21**：⚠️ **会话文件是一份明文、持久的完整 transcript**——里面有它读过的文件内容、工具输出、可能的凭据。它的**文件权限、保留策略、是否需要打码**落在你的范围内（本票只管查询与呈现，不管"谁能读"）。

**票 21 交接来的答案（2026-09-13）**——你交接的三件事都收口了，而且有一条会**改变你的查询层假设**：

- ✅ **文件权限**：创建即 `0700`/`0600`。✅ **保留**：维持不自动清理 + 一个手动 `prune`。✅ **打码在落盘前**。
- ⚠️ **但你的查询层要改一个假设**：**打码发生在事件追加之前**（票 21 第 3 节）——所以**流上的文本 == 模型当时看到的文本**（一致，这点是好事），但**工具执行时用的是真值**。⇒ **"这次调用到底干了什么"不能指望从流里还原真值**；`[REDACTED:<kind>]` 要当成**一等值**显示，而不是当成缺失或损坏。
- 一条与你的 `--files` 视图有关的：`outputs/<tool_call_id>.txt` **过打码**；**`.before` 不过**（`/undo` 的字节还原源，票 21 第 3 节）。
- 一条与"今天花了多少"无关但同类的事实：**打码不改 token 数**（它替换的是文本，长度会变，但那是估算层的事）——所以你的 `stats` 口径不变。
