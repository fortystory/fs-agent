Type: grilling
Status: resolved
Blocked by: 15, 25

## Question

决定渲染接缝。**本票已改写**：原先的"一条总线还是两条"归到票 15（事件流骨架）去了，本票专注**消费者侧**。

**为什么有架构代价**：三个需求不能靠 `println!` 同时满足 ——

- headless 模式要求 **stdout 只放结果、日志走 stderr**（旧图切片 8/14，否则无法管道化）
- 综述第 13 节的最小可用要求流式输出 + 每个工具调用一行可读摘要
- 全屏 TUI（alt screen、可折叠工具输出、diff 语法高亮、状态栏显示 token / 花费 / 权限模式）

**加上多 agent，第四个需求出现了：同时展示 N 个 agent 的活动。**

要回答：

1. **消费者的接口。** 三个（或四个）消费者如何订阅同一条流？它们各自维护什么状态（TUI 要维护可折叠区、状态栏；plain 只维护"打到哪一行了"）？谁是同步的、谁是异步的？
2. **多 agent 的呈现。** 讨论者并发/轮次进行时，plain 输出怎么不糊成一团？至少要有：发言归属前缀（票 17 已定「合并 + 正文前缀」的编码，但终端呈现是另一回事）、轮次分隔、分歧标记。**headless 的 stdout 纯净性要求在这里最容易被破坏**——多 agent 的状态更新天然想打到 stderr 以外。
3. **进程模型。** 综述记录 **opencode 把 TUI 与 agent server 拆成两个进程**（client/server，TUI 可替换、可远程）。v1 跟不跟？还是同进程内的几个渲染器？
4. **终止原因的表达。** 沿用票 15 定的显式枚举（`completed | max_iterations | aborted | mistake_limit | error` + 讨论专属原因），状态栏与 plain 都要能显示。
5. **一个新的事实需求**：TUI 库选型（ratatui 的当前状态、依赖重量、与 tokio 的配合方式）。票 08 的研究产物没覆盖，本票可能需要**再派一次 research**。
6. **明确不做**：diff 语法高亮之外的编辑器能力（不做内置编辑器）。

**票 15 交接来的事实（2026-09-13）**：

- **消费者的事件来源**：`MessageCompleted { role, text, reasoning? }`（**一条完成的消息——日志里没有增量文本**）、`ToolCallStarted` / `ToolCallCompleted`、`UsageRecorded`、以及各循环结束事件上的 `StopReason`。
- **第 4 条的枚举已经定死**：`Completed | MaxIterations | Aborted | MistakeLimit | Error` + 讨论三类 `Consensus | NoDivergence | RoundsExhausted`（**一个枚举、三层循环共用**，挂在 `TurnEnded` / `RoundEnded` / `SessionEnded` 上）。
- **第 1 条的接线形状因此有个新岔口**：增量**不进日志**，走**传输层旁路**直达渲染器。所以"订阅同一条流"要么订阅两个来源（持久流 + 增量通道），要么让 writer 在落盘前把增量广播出去。这是你要选的形状。
- **第 2 条（多 agent 呈现）的素材齐了**：每条事件带 `speaker_id`（`Debater(id) | Executor(id) | User | System`）；`RoundStarted { round, mode }` / `RoundEnded` 给轮次分隔；`DivergenceRecorded { round, topic, positions }` 给分歧标记。
- **headless 的 stdout/stderr 分流可以照事件分类切**：`SessionError { code, detail }` 是会话级运行失败（**模型看不到**），`AgentError { message, recoverable }` 要进模型上下文。前者天然属于"给人看的诊断"，后者天然属于"给模型的 prompt"。
- 第 5 条那个"可能再派一次 research"的判断仍然成立——票 08 与票 24 都没覆盖 **ratatui 的当前状态**。

**票 05 交接来的事实（2026-09-13）**：

- 渲染器需要一个**"等待用户回答权限询问"**的状态：询问是 `PermissionAsked` 事件，回答产生 `PermissionDecided`。但**不要预设"每次写操作都会弹询问"**——hook 可以把 `ask` 收紧成 `deny`，于是**询问根本不发生**（票 05 说这是 hook 阻止询问的唯一方式；原型剧本 4 演示）。所以询问态必须由流驱动，不能由"工具是写类"推断。
- **`PermissionDecided` 在自动放行时也会产生**（`source: Policy`；另有 `User` / `Hook`），所以"权限模式 / 最近一次裁决"可以从流上直接渲染，不需要另存状态。
- **PostToolUse 的 hook 反馈在流上是独立的 `HookExecuted` 事件，但模型看到的是一条合并后的 tool 消息**（投影合并，因为 provider 只允许一个 `tool_call` 对一条 tool 消息）。渲染侧显示成两条还是一处，由你定。

**票 10 交接来的事实（2026-09-13）**：

- **状态栏要显示"当前模式"**（你第 3 条已列了"权限模式"）。plan 模式是 `readonly` / `ask` / `auto` 之外的第四个**策略预设**，判据是"**只允许 `effect() == ReadOnly` 的调用**"——所以状态栏可以说得更具体（"只读（计划）"），而不是一个空泛的 "plan"。
- **模式本身不在流上**（票 10 第 6 节）：进出 plan 模式**不产生事件**，所以状态栏的数据来源是**本地状态 + 用户手势**，不能从流里读。要显示"为什么这个调用被拒"，读 `PermissionDecided.why`（会被填成"plan 模式：禁止写"之类）。
- **"覆盖 / 追加 / 保留"是进入模式时的一次手势交互**（`/plan` 撞上已存在的 `PLAN.md` 时问一次），**不是流上的事件**——它是 CLI/TUI 的提问，产出的是对文件的处置。
- 顺带：`PLAN.md` 的写入是 plan 模式下**唯一被放行**的写，所以会出现一条很反常的组合（模式是只读，却有一次写成功）——别把它当 bug。

## Answer

**已定（2026-09-13，grilling 两轮 + 一个 research 票）。** 事实来源：`research/06-tui-and-highlighting-crates.md`（票 25 的产物，712 行）。

### 1. 进程模型与渲染器的基数（票面第 3 条）

**同进程；渲染器是启动时选定的一个。**

- 三个消费者其实是**互斥的模式**（headless 与全屏 TUI 不可能同时画在同一个终端上），所以它是**一个 trait 的三个实现**，不是"多个订阅者如何共存"。
- **不做两进程**（opencode 形状）：① 自用单前端，而综述把 event-stream 架构标 ⬜ 的理由正是"只对多前端 / 多 runtime 才有回报"；② 两进程要把整条流 IPC 一遍（序列化 + 背压 + 生命周期），而票 15 刚把"单一写入者 + 一条流 + `seq` 是唯一身份"钉好；③ "TUI 崩了不丢会话"这个真需求由票 07 的会话文件 + `--continue` 满足。
- 同进程的白送好处：**增量旁路不需要序列化**。
- **代价与缓解**：渲染 bug 能拖垮会话 → **渲染任务的 panic 由循环捕获成一条 `SessionError`，并降级到 plain 继续**。

### 2. 消费者的接口（票面第 1 条）

**一个 trait、三个实现；每个模式一个独立任务，消费同一条广播通道。**

- **trait 面**（形状，不是最终签名）：`Renderer { on_render(&mut self, r: RenderItem); on_input(&mut self, i: Input); finish(&mut self) }`，其中 `RenderItem = Event(&Event) | Delta(&Delta)`。
- **通道由组装期注入**：`EventLog` 的 writer 在追加后**广播**，`agent` 循环把 provider 的**增量**转发到**同一条**通道。两个理由：
  1. 让 `events` 与 `render` **没有新增边**（`render → events` 本来就在票 01 的 DAG 里；投递是经**组装期注入的通道**，不是互相调用）（谁都不 import 谁，通道是 `cli` 组装的），DAG 不斜；
  2. **增量与日志事件必须同一条通道**——分两条的话，两者的相对顺序就无定义了（正是票 15 里"多总线要额外保证顺序"那条论证）。
  这也回答了票 15 交接的那个岔口：**取"writer 广播"那一支，并让增量也投进同一个广播**。
- **各自维护的状态**：
  - **plain**：只维护"打到哪儿了"——当前是否有未换行的流式行、上一次的行首前缀是谁（决定要不要换行 + 重打前缀）。**无历史**。
  - **TUI**：折叠块（key = `tool_call_id`）、视口 / 滚动、状态栏（模式 / token / 花费 / 轮次 / 停），以及输入行。
  - **headless**：无状态，只有两个 sink 与一条"这段是不是最终产物"的判据。
- **同步 / 异步**：**三种模式共用同一个形状**——都 `tokio::spawn` 一个任务消费广播，差别只在实现里。TUI 额外 `select!` 在（广播 / tick / 键盘）三者上——**ratatui 官方示例与官方模板正是这个形状**；crossterm 的 `EventStream` 官方实现内部自建线程，直接用即可。plain / headless 不需要定时器，只消费广播。
  - **统一形状是有意的**：接线只有一条路径，TUI 与另两者不会各自长出一套。
- **输入归渲染器**：终端由渲染器独占，键盘输入也归它；它把答案（例如权限询问的回答）通过**一个注入的 answer channel** 送回循环。这样"谁拥有终端"只有一个答案，plain 与 TUI 不会抢 stdin。

### 3. 多 agent 的呈现与 headless 的纯净性（票面第 2 条）

- **发言前缀逐行**：`[kimi]` / `[deepseek]` / `[executor:<id>]` / `[user]`，**每行都带**——多 agent 交错时"这一段是谁说的"必须逐行可判。
  - ⚠️ **与票 17 的正文前缀是两回事**：票 17 那个是**发给模型**的（`[architect] …`），这里是**给人看的**。**不要共用同一个字符串生成器**——两个消费者、两套需求，改一个不该牵动另一个。
- **轮次分节线**：`RoundStarted { round, mode }` 打一条（`── 第 2 轮（定向） ──`）；`RoundEnded { reason }` 打一行收尾。
- **分歧缩进块**：`DivergenceRecorded { topic, positions }` 打成一个块（主题 + 各方立场）——它是这一轮最值得人看的东西，不该挤成一行。
- **工具调用一行摘要**（综述的最小可用要求）：`ToolCallStarted` 打一行（名字 + 关键参数摘要），`ToolCallCompleted` **在同一行收尾**（耗时 + ok/err）。TUI 里这两个事件就是折叠块的开始 / 结束。
- **hook 反馈显示成一处**（回答票 05 交接的那个"由你定"）：日志里 `ToolCallCompleted` 与 `HookExecuted` 是两条事件，但**渲染的单位是"人对这次工具调用的理解"**——按 `tool_call_id` 归成**一个**折叠块，hook 反馈作为块内的附加行。这与投影的单位恰好一致（投影也把它们合并成一条 tool 消息）。
- **自定义工具的名字**：流上保持 `custom__<ns>__<tool>`（规则与审计用原样），**呈现时缩写**成 `<ns>/<tool>`——缩写只发生在渲染层。
- **headless 的纯净性用结构保证**（关键的一条）：**渲染器不直接 `println!`**，它只写**两个显式 sink**（`stdout_result` / `stderr_diagnostic`），由模式决定谁接哪个。
  - **stdout 的内容判据**：放**最终产物**——`TurnEnded { reason: Completed }` 或讨论合成（`Consensus`）时的 assistant 文本，逐字流式；**其余全部 stderr**（工具摘要、进度、诊断）。
  - 分流可直接照票 15 的事件分类：`SessionError { code, detail }` 天然是给人看的诊断（stderr）；`AgentError { message, recoverable }` 天然是给模型的 prompt（它进流与模型上下文，不是 stdout）。
  - 价值：把"多 agent 的状态更新想打到 stdout"这种事故变成**结构上难发生**，而不是靠自觉。

### 4. 终止原因的表达（票面第 4 条）

**直接沿用票 15 的 `StopReason`，不新增任何东西。**（票 18 后来给这个枚举加了第 9 个值 `BudgetExhausted`——值的集合以票 15 的答案为准）

- plain 在 `TurnEnded` / `RoundEnded` / `SessionEnded` 各打**一行**（值 → 人可读标签）；TUI 进状态栏。
- 一条硬要求：**`Completed` 与 `Aborted` / `Error` 不能显示成同一种颜色**——"正常收尾"与"撞墙退出"必须一眼可分。这正是综述推荐显式枚举的理由（比布尔"完成没完成"信息量大得多）。
- 建议：`MistakeLimit` / `MaxIterations` / `RoundsExhausted` 这类"撞墙"值**带上撞的是哪个上限**，否则用户看到 `MaxIterations` 也不知道该调哪个旋钮（阈值归票 18）。

### 5. TUI 栈（票面第 5 条）

- **库 = `ratatui 0.30.2` + `crossterm`**（默认特性）。
  - `tui-rs` **已废弃**（README 逐字 "no longer maintained" + 仓库 Public archive，硬证据）；`cursive` 仓库还活着但**没有维护声明**（⚪）；crossterm 是 ratatui 的**默认后端**，而且**官方 tokio 示例（`examples/event-stream-tokio.rs`）与 ratatui 官方模板都在它上面**——默认路径就是上游 CI 覆盖最厚的路径。
  - 实测闭包：ratatui 默认 **70**；关默认特性 + crossterm 可到 **62**；termion 后端只要 **45** 但离开默认路径且维护声明是 ⚪；termwiz **118**。**不为省十几包去换非默认后端**（是否关默认特性省 8 包 → `/to-spec`）。
- **viewport = inline，不用 alt screen**：
  - **已定稿的内容用 `Terminal::insert_before` 推进正常 scrollback**，**live 的内容留在 `Viewport::Inline(u16)` 那块定高底部区**（状态栏 + 输入 + 正在流的输出）。`init_with_options` **只开 raw mode、不进 alt screen**，正是这条路。
  - 理由：**转录留在正常终端历史里**——可滚动、可复制、可用既有工具；alt screen 会把它隔离起来，退出即消失。对一个 coding agent 的转录，那是真实损失。
  - **代价（官方列明的限制）**：全宽、锚定光标行 col 0、高度被钳制、可能引发终端滚动、无 scrolling-regions 时需清屏重绘。可折叠区因此比全屏少——**折叠只在 live 区里发生**。
- **语法高亮 = `tree-sitter-highlight 0.27.0`**：
  - **树已经在**：它要求 `tree-sitter ^0.27.0`，正是票 12 要拿的那个大版本（+ `tree-sitter-rust`）；闭包 **15**。
  - 相对地 `syntect` 闭包 42 / 44，且**默认路径要用 `cc` 编译 Oniguruma C**（官方 Readme 自承构建困难）——票 25 刚把"N 包 + 有没有 C 工具链"当成选型事实，就不该在自己身上重新引入一个 C 构建依赖。
  - **代价诚实说**：`tree-sitter-highlight` 的条目里**只有 `HtmlRenderer`，没有终端渲染器**——"scope → 颜色"的映射要自己写。但这本来就是要我们定的**视觉决策**（哪些 scope、什么色），自己写反而把控制权拿在手里；24bit 转义本身是十几行的事。
  - **diff 着色**（±行色 + 词级差异）与语法高亮是**两层**：前者不依赖任何库。
- **终端能力探测用 `std::io::IsTerminal`**（1.70 稳定，官方 TTY 判定）。crossterm 的 `tty::IsTty` 在**未发布的 master 上已被删除并建议改用 std**——不要依赖它。⚠️ **alt screen 的支持探测 API 不存在**（⚪）——这是选 inline 的又一个附带好处：不需要探测。

### 6. headless 下的权限询问

**`Ask` 自动降级为 `Deny`，理由写进 stderr 与 `PermissionDecided.why`。**

- headless 的定义就是"可能没有终端"，所以不能等 stdin（要 TTY 才能读）。
- 要非交互地放行，正确的位置是**策略**（票 20 的规则语言），而不是让 headless 挂在一个可能不存在的输入上。
- 降级由谁做：**循环在权限门外**（"有没有交互能力"是运行期事实，不是策略），但**理由必须落到事件里**，否则事后看不出"这次拒绝其实是因为没有终端"。

### 明确不做

- 不做内置编辑器（只做"diff 着色 + 代码高亮"，票面第 6 条）。
- 不做两进程（第 1 节）；不做 alt screen（第 5 节）；不做 `syntect` 那条 C 构建路径（第 5 节）；渲染器不直接 `println!`（第 3 节）。

### 交接

- **票 01**：`render` 与 `events` **没有新增边**（`render → events` 本来就在票 01 的 DAG 里；投递是经**组装期注入的通道**，不是互相调用）——广播通道由 `cli` 在组装期创建并分别注入（writer 拿 sender、渲染任务拿 receiver）。所以 12 个顶层边界之间**没有新增边**。
- **票 15**：你交接的那个岔口取了"**writer 广播**"那一支，并且**增量也投进同一个广播**（分两条通道则相对顺序无定义）；因此 writer 需要一个"追加后发布"的动作，而**通道是注入的**（`events` 本身不认识 `render`）。
- **票 17**：渲染的**人看前缀**与投影的**模型看前缀**是两套——**不要共用字符串生成器**。
- **票 20**：headless 的 `Ask → Deny` 降级由循环做，理由进 `PermissionDecided.why`；如果你更愿意把它表达成策略，那是你的选择，但**降级事实必须留在事件里**。

**票 18 交接来的事实（2026-09-13）**——状态栏要多两个东西，多一个撞墙值：

- **缓存命中率要可显示**：`UsageRecorded` 里现在有 `cached` / `miss` 两个数（票 18 第 6 节），命中率是"我的前缀设计有没有白费"的直接反馈。⚠️ 一个不是 bug 的现象：**Kimi 有 >256 tokens 才缓存的门槛**（低于门槛的请求**不缓存且被丢弃**），所以短会话命中率天然低——别把它显示成"缓存失效"。
- **费用显示必须分开算 `cached` 与 `miss` 的单价**（票 18 第 2 节）：缓存命中通常便宜得多，只显示总费用的话"命中缓存省下的钱"完全看不出来。
- **`BudgetExhausted` 是新的撞墙值**（票 18 第 7 节）：它与 `Completed` **不能同色**——它是"钱花到了上限"，和 `MaxIterations`（轮数）/ `RoundsExhausted`（讨论轮数）是三个不同的上限，显示上要能区分。
- 一条会影响你状态栏语义的取舍：**会话中途不要改任何进入前缀的东西**（模型、工具数组、`reasoning_effort`、钉住的注入，票 18 第 6 节）——所以状态栏上"模型"这一项在一次会话里是**常量**（除非用户换模式），不必做成动态刷新。

**票 19 交接来的事实（2026-09-13）**——你的 live 呈现与它的事后视图是**两套实现，但可以共享格式定义**：

- **同形**：事后时间线也用 `[轮 N · 名字]` 这个形状（票 19 第 3 节），所以两处看起来一致；但按票 17 已经立下的规矩，**"人看的前缀"与"模型看的前缀"不共用生成器**——现在再加一条：**live 与事后**也不必共用生成器。
- **可以共用的**是**格式定义本身**（那个常量的形状），因为两处渲染的是同一件事；共用一个常量能让它们不会各自漂移。
- 事后视图与你**无关的部分**：它是 CLI 的一次性输出（`sessions show/--files`），不是渲染器的第四个模式——所以**不要把事后查询接进你的 renderer trait**，那会让"启动时选定一个渲染器"的形状变复杂。
- 一条与你相关的边界：票 19 的 `stats` 会报**缓存命中率**与**编辑匹配梯的降级分布**——而你的 live 状态栏只报前者（后者不需要 live 可见，它是事后统计）。别把 `stats` 的指标清单照搬进状态栏。

**票 20 交接来的答案（2026-09-13）**：你第 136 行留给票 20 的那个选择（headless 的 `Ask → Deny` 归循环还是归策略）已定——**维持你的默认：循环在门外降级**。

- 理由：**"有没有交互能力"是运行期事实**（取决于启动时选了哪个渲染器），不是一条关于工具 / 路径的策略；把它塞进门会让门的输入多一份状态，而门是**纯函数、不读环境**（票 05）。
- 所以门的裁决**如实保持 `Ask`**（记录"策略要求询问"），**降级发生在门外**，且**理由进 `PermissionDecided.why`**（票 19 要求那个字段始终填）。你显示"为什么这个调用被拒"时，看到的是**一条 `Deny` + `why` 说明它本来是 `Ask`**，不是一个 `Ask` 事件——渲染侧别把它当成"用户拒绝了"。
- 另一条你可能会用的：`.env` 家族现在默认 `deny`（票 20 第 5 节），而**敏感路径的写入永不自动批准**（断路器，票 20 第 4 节）——所以状态栏会看到更多"策略直接拒"的调用，那不是配置错误。
