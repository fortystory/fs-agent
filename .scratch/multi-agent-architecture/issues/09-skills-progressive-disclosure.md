## Answer

**已定（2026-09-12，grilling 与用户逐轮确认）。环境事实为本机实测（2026-09-12）：`~/.claude/skills/` 40 个、`~/.agents/skills/` 38 个，两者 **38 个同名且不是软链**；`SKILL.md` = YAML frontmatter（`name` / `description`）+ Markdown 正文；`disable-model-invocation: true` 在现有 skill 里已被实际使用。**

### 1. 落点与加载机制

- skills 是 **`context` 的子模块**（票 01 已定），不进顶层边界。
- **全文加载 = 一个内建只读工具 `skill(name)`**，返回 `SKILL.md` 正文（去 frontmatter）。产物是**流上的一条 tool result**。
  - **单一收口**：加载只有一处 → 能记"已加载集合"、能按 skill 计量预算、能被权限语言覆盖（票 20 可写 `skill(name)` 这类规则）。
  - **语义正确**：模型自己发起的动作就是 `tool` role，不该伪装成"用户说的"（那是用户 `/name` 手势的语义）。
  - 票 02 的往返记账（每个 tool_call 恰好一条结果）自动覆盖它；票 03 的 `effect()` 对它是 **`ReadOnly`**，天然可并发。
  - 它**追加在对话尾部**，所以**不破坏前缀缓存**——票 06 的注入在头部（钉住），skill body 在尾部（可裁剪）。
- **"一行描述"** = `<name>: <description>`，进**第一条 user message**、钉住、记成事件（票 06 第 5 节），与 `AGENTS.md` 同一条。
- **v1 的 skills 只装指令，不装工具。**

### 2. 发现与加载路径

**项目级 + 用户级，两级各三个来源，同名冲突就近/更专有者胜**：

| 级别 | 路径（左 > 右） |
|---|---|
| 项目 | `<repo>/.fs-agent/skills/` → `<repo>/.agents/skills/` → `<repo>/.claude/skills/` |
| 用户 | `~/.config/fs-agent/skills/` → `~/.agents/skills/` → `~/.claude/skills/` |

**项目 > 用户；own（`.fs-agent`）> `.agents` > `.claude`**——与 AGENTS.md 那条"离被编辑文件最近的赢"同向。给一个配置开关关掉兼容目录（Amp 有 `amp.skills.disableClaudeCodeSkills` 的先例）。

理由：本机这两套库**已经真实存在且 38 个同名**；跟随的成本是多两个路径，不跟随的成本是**现成 skill 全部作废**。

### 3. 与 `AGENTS.md` 的边界（本票自证价值）

自证价值成立：`AGENTS.md` 逐轮全量注入（越长越贵、每轮付费），skills 只在调用时付费。skills 的真实价值 = **把"偶尔才需要的长指令"从每轮成本里拿出去**。

| 内容 | 去处 | 判据 |
|---|---|---|
| 项目事实：构建/测试命令、代码风格、目录约定、硬约束 | **`AGENTS.md`** | "这条指令在 >80% 的轮次里都要生效吗？" |
| 按任务的长指令：发布流程、迁移步骤、某类重构手册、外部系统操作步骤、长参考 | **skill** | "只在特定任务里用得上，或长到不该每轮付费吗？" |
| 必须无条件执行：格式化、跑测试、拒绝某类命令 | **hook**（票 05） | 指令靠模型自觉，hook 是 harness 的保证 |

### 4. 预算与重新注入

- **单 skill 上限 5k tokens**（沿用生态数值）。实测本机最大的 `SKILL.md`（wayfinder，11,908 字节 ≈ 3.0k tokens）也够放 → 这是安全阀，罕见路径。**超限时截断并明确告知**（附"完整内容用 `read_file` 读该文件"的提示），**不是**拒绝加载（拒绝会让稍长的 skill 彻底不可用）。
- **描述清单独立封顶（建议 3k tokens）**：实测 38 个 skill 的 description 合计 5,708 字节 ≈ **1.4k tokens**——可接受但不是零，且"选项一多模型就选错"同样适用于 skill 清单。超了按优先级截断，不无界增长。
- **已加载 skill body 总上限 25k tokens**，超出丢最老的。
- **对票 06 第 3 节丢弃顺序的细化**（插入一类）：

  **老工具结果 → 老 skill body（超出 25k 的最老先丢）→ 老整轮 → 该 Turn 硬失败**（**丢弃顺序以此为准**；票 17 的答案曾把方向写反）

  skill body 比普通工具结果**更黏**：模型正照着它做事，被一条大的 `cargo test` 输出挤掉就等于中途失忆。
- **compaction 后重新注入**：v1 没有 compaction（票 06 已后置），但**"已调用集合"可重算**（从流上推导哪些 `skill(name)` 调用发生过）→ 将来做重新注入**不需要返工**。与票 06 的"摘要记成事件"是同一条原则。
- **`disable-model-invocation: true`**：既不进描述清单，`skill()` 工具也**拒绝加载它**（防止模型猜名字绕过）；只留用户 `/name` 一条路。

### 本票明确不决定的（交接汇总）

- **把工具打包进 skill**（Amp 的反直觉建议：skill 加载前其工具对模型不可见）→ **票 11**（动态工具注册）。v1 的 skills 只有指令。
- 票 06 的丢弃顺序按第 4 节细化（注记在票 06）。
- skills 的**触发文案**与全文加载的具体格式（`/name` 手势的表层）→ `/to-spec` 之后。
- **MCP** 不在范围内（证据型砍掉项）。

**票 11 交接来的答案（2026-09-13）**：你第 77 行交接的那个设计选项（"把工具打包进 skill"）已定。

- **答案是"不挂 skill"：动态工具启动即全局可见，工具集在组装期固定。** 决定性理由是**缓存前缀**——`tools` 数组是请求**前缀**的一部分（票 02 的线级形状 + 票 06 的"逐轮不变才保住前缀缓存"）；**中途增删工具 = 前缀变化 = 丢掉那张"免费的 5~10 倍成本差"**。你第 35 行那条"skill body 追加在**尾部**所以安全"的推理**恰好说明了工具为什么做不到**：工具在头部。
- **Amp 的顾虑用你的机制接住**：动态工具**能不能被调用**是**权限门**的事，不是可见性的事。所以"某些工具只在某 skill 加载后才可用"如果要做，正确位置是权限规则（门的输入里能看见已加载的 skill 集合）——**票 20 的可选项**，已交接。
- 与你互补的一点：动态工具的名字带 `custom__<ns>__<tool>` 前缀（票 11 第 3 节），**而内建工具名永不含 `__`**——所以"这是个自定义工具"在名字上就能判定；将来若真做"按 skill 限定工具"，这个谓词就是规则的写法。
- 另一处相邻边界：**你第 64 行"超限截断并提示用 `read_file` 读全文"与票 07 的落盘指针是同一形状**（大内容在流外、指针在流内）——两处不必统一实现，但口径一致。
