## Question

**本票是从旧图「极简型」砍掉项里重开的**，而且它已经被新事实**顶开**——不再是"自用场景人工看着就够"能打发的东西。

旧图砍掉它的原文理由是："保留『前缀稳定』这一条免费优化即可"，砍掉的是**显式 cache 断点调优、硬预算上限、弱模型分流**。现在：

- **N agent × 多轮 × 递增上下文是乘法增长**：2 个讨论者 × 最多 3 轮 = 6 次调用，每次都要重放增长中的历史；派出的执行者再叠。
- **Kimi 限流含 TPD**（按充值分档的**日** token 上限，见 map 的 Notes）——撞上就是**当天不可用**，不是慢一点。
- 旧图切片 11 只保留了"每轮 + 累计 token/费用显示"。**显示不等于限制**（综述原话：opencode 连预算机制都没有，"说明『显示』和『限制』是两件事"，而业界普遍只做前者）。

要回答：

1. **预算的单位与归属**：按会话总量、按 agent、还是按轮次？讨论者与执行者共享一个池子吗？
2. **硬停行为**：超预算时是**中断整个讨论**、**降级为单 agent**、还是**只警告**？中断要让讨论的状态可恢复（接票 07 的落盘）。
3. **前置估算**：能不能在开一轮之前估算"这一轮要花多少"（轮数 × N × 预估上下文），从而**拒绝**开这一轮？这比事后中断更省。
4. **弱模型分流的重开。** 综述标 🔷（aider 的 `--weak-model` 跑 commit message；Claude Code 的权限分类器跑在更便宜的模型上；Cline 允许 Plan/Act 配不同模型）。**多 agent 下"模型分工"已不只是省钱手段**——异构是多样性来源（票 16）。所以本票要定：除了两个讨论者之外，还有哪些调用可以用便宜模型（合成？裁判？摘要？）？
5. **前缀稳定性的落地。** 综述把「system prompt 前缀稳定」标 ✅，称其为"免费的 5~10 倍成本差"。多 agent 下每个 agent 的前缀各自稳定——**投影（票 17）会不会破坏它**？合并算法若把内容顺序变动，缓存就废了。这条要显式检查。
6. **cache 计量**：综述建议照抄 Amp 的字段设计（`cache_creation_input_tokens` / `cache_read_input_tokens` 分开计量），因为**这是判断缓存有没有生效的唯一办法**。两家的 usage 里有没有这些字段？（若 `research/02` 没覆盖，需补一次 research。）
7. **TPD 感知**：要不要读 Kimi 返回的限额响应头/错误并在接近上限时提前收敛讨论？

**票 06 交接来的前提（2026-09-12）**：**会话级累计 token 是从 `EventLog` 上的 `Usage` 事件求和的派生值**（票 02 已把两家 usage 归一），不是隐藏状态——本票可以直接站在它上面做硬停（票 06 第 4 节）。**TPD 不折进窗口预算**，它的归属正是本票。另两处交界：窗口预算 `usable_input = caps.context_window − min(20_000, caps.max_output_tokens)` 由票 06 定；`trim` 是**只读视图**、不动日志，所以裁剪本身不会打乱缓存前缀，但**合并算法若让内容顺序变动就会废掉缓存**（本票第 5 条，与票 17 交界）。

**明确不做**：按任务维度的成本报表、多模型跑分 dashboard（属证据型砍掉项）。

## Answer

**已定（2026-09-13，grilling 两轮）。** 前提来自票 06（窗口预算与会话累计分离）、票 14（执行者轮数独立、钱共享）、票 16（讨论的调用数与缺席语义）；缓存字段的事实来自 `research/02` §5–6（**已覆盖，不需要补 research**）。

### 0. 先纠正票面的一个前提

**TPD 只存在于 Tier0**（累计充值 ≤ \$1，1,500,000 tokens/日）；**Tier1（\$10）以上就是 `Unlimited`**（`research/02` §6.1 的档位表逐行）。所以"撞上 TPD 就是当天不可用"对**多数充值用户不成立**——真正日常的风险是 **RPM / TPM / 并发**（票 02 的 adapter 已在处理 `Retry-After` 与有界重试）。这不是说 TPD 不用管，而是**别把它当成主要风险来设计**：票面第 14 行的措辞需要按事实收窄。

### 1. 预算的"单位与归属"：三个量，各管一段（票面第 1 条）

| 量 | 归属 | 谁定的 |
|---|---|---|
| **窗口**（能不能发得出去） | **按 agent 各自的模型**算 | 票 06 |
| **轮数**（跑多久） | 讨论 **2**、执行者 **25**——**两个独立旋钮** | 票 16 / 票 14 |
| **token 累计**（花多少） | **会话级，且讨论者与执行者共享这一份账** | 票 06 / 票 14 |

⇒ **本票要定的是第三个**。它不是隐藏状态：**会话累计 = 从 `EventLog` 上的 `UsageRecorded` 求和的派生值**（票 06）；执行者的事件在同一条流上，所以它**自动计入**，不需要另开账本（票 14）。

### 2. 硬停：盯累计，行为 = 降级并收尾（票面第 2 条）

- **不"只警告"**：综述原话——opencode 连预算机制都没有，"说明『显示』与『限制』是两件事"，而业界普遍只做前者。**显示已经有了**（票 06 的派生累计 + 票 13 的状态栏），本票补的是**闸门**。
- **不"立刻中止"**：那会把已经付过钱的工作丢掉。最省的是**把手头这轮跑完、不再开新的**：
  - **讨论**：不再开第二轮，**直接进合成**——合成是**唯一不能省**的调用，否则整个讨论白花钱；
  - **执行者**：不再派新的；**已在跑的跑完**（钱已经花了，掐掉只会两者皆失）。
- **降级不是新机制**：票 16 已经能让讨论表达"某一方缺席"，所以"降级为单 agent"就是**别让另一方再说话**。
- **可恢复**：收尾写进事件（票 07 的落盘保证"停在哪"可恢复）。
- **闸门用 token，费用只作显示**：token 是 provider 直接给的、可精确求和的量；费用要一份**可配的价目表**（价格会变），而且**必须把 `cached` 与 `miss` 分开计价**——否则命中缓存省下的钱在显示上完全看不出来（第 6 节刚把这两个数变成一等字段）。

### 3. 前置估算：做，但阈值是"剩余额度的比例"（票面第 3 条）

- **用来估的量都已知**：票 16 给了确切的调用数（无分歧 3 / 有分歧 5）；执行者最多 25 轮（票 14）且**每轮重放它自己**的历史（历史里有工具结果，所以它的上界比讨论者高）；单次输入用票 06 的字符/4 估算 + `max_output_tokens` 作输出上界。
- **诚实说它必然偏保守**：票 06 的估算本来就是"字符/4"，**它没有精确到能当计费**。所以阈值用**剩余额度的比例**（例如剩余 20% 才触发前置拒绝），而不是"估算 > 剩余"——否则粗估会频繁误拒。
- **它比事后中断省**：被拒绝的那一轮**一次调用都没发生**。

### 4. 弱模型分流的落点（票面第 4 条）

**只有两个落点：合成器与执行者；讨论者绝不能换。**

- **讨论者绝不能换**：异构是多样性的**最强杠杆**（研究），换掉就把讨论的价值抹了；Chart 期也已定"不允许加同模型的第三个角色"。
- **执行者**：票 14 已经留好覆盖点（默认继承派出者、可配覆盖）——**不需要新机制**。
- **合成器**（票 16）：一次独立单发调用、无工具、输入是两份回答——天然候选。但**它是本图的核心产出**（画出选项空间），别为了省钱把它做坏。
- **裁判没有**：票 16 用的是机械判定，所以这一项不存在。
- **v1 默认全用讨论者的模型**：**机制留好，但"哪个调用适合便宜模型"目前没有数据**——先让贵的跑通、看真实花费分布，再决定把哪一个换便宜。（与票 04 拒绝 `edit_format`、票 14 不做专职角色同一条：**机制先于取值**。）

### 5. TPD / 限额的感知（票面第 7 条）

**被动为主 + 本地日账本；不读响应头、不猜额度。**

- **没有任何限额响应头被文档化**：我核过 `research/02` §6——通篇没有 header 字段，唯一被文档化的信号是 **429 `rate_limit_reached_error`**，它把组织级**并发 / RPM / TPM / TPD** 触顶合在同一个错误里。→ 若将来发现响应头存在，加进来是**局部改动**（⚪ 未证实）。
- **被动**：429 按票 02 的分类处理（`RateLimited` 与 `QuotaExhausted` **必须分开**，两家错误码不同），触顶时按第 2 条的降级策略收尾。
- **本地日账本**：把 `UsageRecorded` 按 **UTC 日**聚合，用户配一个日上限，接近时提前收敛。
- **日账本是派生的，不是新状态**：启动时扫**今天的**会话文件（按 mtime 过滤）累加，运行中增量累加。零新写入者、零一致性风险，而且它就是"日志 + 规则"的函数——只是那份日志**跨会话**（与票 06 的"预算不是状态，是函数"同一条纪律）。独立日账本文件要多一个写入者和一套一致性纪律（票 15 刚把"单一写入者"钉死），不值得。

### 6. 缓存计量与稳定性（票面第 5、6 条）

**把 cache 计量做成 `UsageRecorded` 的一等字段，归一成 `cached` / `miss` 两个数。**

- **事实已经齐了，不需要补 research**：Kimi 是 `usage.cached_tokens`；DeepSeek 是 `usage.prompt_cache_hit_tokens` / `usage.prompt_cache_miss_tokens`（且 `prompt_tokens = hit + miss`），另有 `prompt_tokens_details.cached_tokens`（= hit）。语义清楚且能对齐。
- **不要照抄 Anthropic 的 `cache_creation` / `cache_read`**：那套字段在这两家**不存在**；照抄会得到一个永远填不满的结构。
- **为什么要它**：综述说这是"判断缓存有没有生效的**唯一办法**"；而**命中率是要显示的**（票 13 的状态栏）——它是"我的前缀设计有没有白费"的直接反馈。
- **两条已知会破坏缓存的操作（本票的实际价值在这里）**：
  1. **Kimi 的 `reasoning_effort` 切档会破坏 prefix-cache 命中**（官方明说"换档应在 session 开始前定好"）⇒ **该字段必须在会话开始前定死，中途不可改**。
  2. 投影侧的内容顺序——票 17 已保证（合并保序、严格按 `seq`、不跨轮、钉住注入不参与合并）。
- **一个不是 bug 的现象**：**Kimi 有 >256 tokens 才缓存的门槛**（"previous request's prompt tokens exceed 256"，否则**不缓存且被丢弃**）——短会话的命中率天然低。
- **票面第 5 条的落地**：投影侧已保证，所以剩下的纪律只有一条——**会话中途不要改任何进入前缀的东西**：模型、工具数组、`reasoning_effort`、以及钉住的注入。

### 7. 预算耗尽的终止值

**给 `StopReason` 加第 9 个值 `BudgetExhausted`。**

- **加值是加法，不是改语义**：票 15 那个枚举是"一个枚举被三层循环共用"，加一个值**不影响任何既有值的含义**。
- 它正是票 13 那条要求的直接实现：**"撞墙值要带上撞的是哪个上限"**——预算是一个确定的、用户可调的上限，与 `MaxIterations` / `RoundsExhausted` 同类。
- 用 `Aborted` 会让它变成**垃圾桶**（用户中断与花钱撞顶是两件完全不同的事）；用 `Error` 语义错。
- **使用者是 `RoundEnded` 与 `SessionEnded`**：执行者不会因预算被拦（已在跑的让它跑完）。

### 明确不做

- 按任务维度的成本报表、多模型跑分 dashboard（票面已列）。
- 立刻中止式硬停（第 2 节）；绝对值阈值的前置拒绝（第 3 节）；v1 就给合成器换便宜模型（第 4 节）；读限额响应头（第 5 节，无文档支持）；照抄 Anthropic 的缓存字段（第 6 节）；独立的日账本文件（第 5 节）。

**票 17 交接来的事实（2026-09-13）**——投影直接改动了 token 账，而且**它同时是你第 5 条（前缀稳定性）的答案**：

- **三条直接影响成本的决定**：**别人的工具结果正文不投**（省大头）、**别人的 `reasoning_content` 不投**（省推理 token）、而**我自己的 `reasoning_content` 必须回放**（票 02：DeepSeek 带 tools 不回传直接 400）——**最后这条是成本项，不是可选项**，做预算时必须把它算进"每轮重放"里。
- **第 5 条（前缀稳定）的答案**：合并算法**保序、严格按 `seq`、不跨轮**，所以内容顺序不会漂移；而且**钉住的注入（AGENTS.md + skill 清单、plan 模式那条指令）不参与合并**——否则每轮合并都会动前缀、缓存当场失效。你的第 5 条可以按"投影侧已经保证"来收口。
- **一个具体的成本形状**：投影现在是"**每个非我发言者一段，带 `[轮 N · 名字]` 前缀**"——前缀是**每轮每人一份**的固定开销，而你的轮数上限正好乘在它上面（2 个讨论者 × N 轮 = 2N 份前缀 + 2N 次递增重放）。
- 顺带：**执行者的每一轮也要重放它自己的历史**（票 14 的交接已记），而它的历史里同样会累积工具结果——投影对**执行者自己**是全量的（票 17 第 6 节），所以执行者的重放比讨论者贵。

**票 16 交接来的事实（2026-09-13）**——一组**确切的调用数**，你可以直接拿它做前置估算（你的第 3 条）：

- **一次讨论 = 3 次或 5 次调用**：**无分歧 = 3**（2 个独立首轮并发 + 1 次合成）；**有分歧 = 5**（2 独立 + 2 定向 + 1 合成）。**没有额外的"判定"调用**——分歧判定是**机械比较两行结论**（票 16 第 1 节），零成本。
  - 注意这与"每轮都是 2 次"的直觉不同：**第二轮只在结论不一致时开**，而那个判定不花钱。所以你的乘法模型要写成 `2 + (冲突 ? 2 : 0) + 1`。
- **瞬时并发 = 2，而且分属两家 provider**（票 16 第 6 节）：两个讨论者并发发，所以 RPM/TPM 尖峰**天然摊到 Kimi 与 DeepSeek 两侧**，而不是把一家的额度翻倍。这对你的第 7 条（TPD 感知）是好消息：讨论本身的瞬时压力不大，真正的风险是**日累计**。
- **合成器是你第 4 条（弱模型分流）的第一个真实用户**：它是一次**独立的单发调用**（无工具、无回合，票 16 第 2 节），输入只有两份回答 + 两行结论。它是"用便宜模型"的天然候选——但要先确认**弱模型能不能胜任"画出选项空间"这件事**（它是本图的核心产出，别为了省钱把它做坏）。
- **两个旋钮别混**：讨论的轮数上限是 **2**（票 16 第 4 节），执行者是 **25**（票 14 第 2 节）。
- 一条**对你的硬停直接有用**的事实：**单侧失败时讨论会继续**（票 16 第 5 节）——所以"一方挂了你还要不要继续烧钱"这个判断出现在这里，而不是在讨论结束时。那正是你第 2 条（硬停行为）要选的东西：`QuotaExhausted` 撞上时是中断整个讨论、还是降级为单 agent 继续。**本票给了一个现成的形状**：讨论协议本来就能表达"某一方缺席"（票 16 第 5 节），所以"降级为单 agent"不是新机制，而是**把一个已经存在的状态用起来**。
