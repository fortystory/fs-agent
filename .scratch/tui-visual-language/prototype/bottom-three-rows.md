# 底部三条（状态行 / 输入区 / 提示行）（prototype）

对应 [底部三条](../issues/06-prototype-bottom-three-rows.md)。**一次性素材**；对着真终端看：`python3 .scratch/tui-visual-language/prototype/bottom-rows-demo.py`（它按 `hint_line` / `status_row` 的算法**重算**实际宽度，不是估的）。

## 布局事实（读代码得到）

```
<转录>
┄┄┄┄┄┄┄┄┄┄   ← panes.input.y - 1
<状态行>      模型 kimi │ 询问 │ 上下文 42%
<输入区>      ❱ 草稿（3–10 行）
┄┄┄┄┄┄┄┄┄┄   ← panes.hints.y - 1
<提示行>      就绪 · enter 发送 · … · ctrl-c/ctrl-d 退出
```

- **状态行**：整行一个 `DarkGray`（`tui.rs:3935`），内容是 ` 模型 X │ Y │ Z `（`wording.rs:1697-1713` 的三档降级）。
- **提示行**：整行一个 `DarkGray`（`tui.rs:4531`），拿到的宽度是 **`panes.hints.width` = 主列宽**。
- **输入区**：整段 `BOLD`（`tui.rs:4515`）；只有提示符那个 span 单独上专色（`4507-4512`）。
- 两条横虚线都在（`input.y-1` 与 `hints.y-1`，`tui.rs:3726`）—— **[`tui-chrome/spec.md:196`](../../tui-chrome/spec.md) 当初还给转录的那一行空白，就在状态行上方那条虚线之上**。

## 核心问题：提示行的宽度是主列宽

`hint_line` 的注释自己写着：「**宽屏带着左栏时提示行比屏窄 41 列**，所以屏宽 120 的帧上只看得见四条提示」（`wording.rs:1181-1182`）。重算结果：

| 屏宽 | 左栏 | 提示行宽度 | 实际显示 |
| --- | --- | --- | --- |
| 120×24 | 40 | **79** | **4/6 条**：`enter 发送 · ctrl-j 换行 · esc 取消 · shift+tab 模式` + 出口 |
| 80×24 | 28 | **51** | **2/6 条**：`enter 发送 · ctrl-j 换行` + 出口 |

**全部 6 条 + 出口 + 状态词 = 111 列**（脚本实测）。120 列屏给提示行 79 列，差 **32 列**。

而 `ctrl-o 左栏` 按 `KEY_HINTS` 的顺序排在最末（`wording.rs:1136-1143`，`sidebar-toggle` spec §4 定的：滚动比它常用）—— **于是左栏自己的开关，是最不可能出现的那一条。**

## 待拍板 1：提示行怎么拿到宽度

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| **A 跨整屏** | `panes.hints` 从主列宽改成整屏宽；左栏从「全高」改成「到提示行为止」 | 左栏页区少 1 行（120×24 下 15 → 14）；撞 [`sidebar-toggle`](../../sidebar-toggle/spec.md) / [`trace-tab`](../../trace-tab/spec.md) 写下的「全高」 |
| **B 减条目** | 维持主列宽，把 `PgUp/PgDn 滚动` 与 `ctrl-o 左栏` 从提示行移走（进 `/` 菜单的帮助） | 这两条在屏幕上永远不可见 —— 而 `ctrl-o 左栏` 正是「叫回左栏」这件事的唯一提示 |
| **C 保持现状** | 承认宽屏也只看得见 4 条 | 痛点原样保留 |

➡️ 推荐 **A**。理由：41 列被吃掉不是设计，是「左栏全高」这条决定的副作用；而提示行想说的东西里就有「怎么收起那块吃掉 41 列的东西」。**代价写得明明白白：左栏页区少 1 行。**

## 待拍板 2：状态行的三段层次

现状整行一个色、只靠 `│` 分。05 已经把这一行归**过程档（`MUTED`）**，但行内仍可分层：

| 方案 | 做法 |
| --- | --- |
| **A 标签退、值进** | 标签（`模型` / `上下文`）用 `MUTED`，值（模型名 / 模式名 / `42%`）用 `PLAIN`，`│` 用 `CHROME` |
| B 只换分隔符 | 整行 `MUTED`，`│` 换成 `CHROME` |
| C 保持整行一个色 | 不动 |

➡️ 推荐 **A**：「值比标签重要」是这一行唯一真实的层级，而且它不需要任何新颜色 —— 用的正是 05 给的四种手段（`PLAIN` / `MUTED` / 结构）。

## 待拍板 3：状态行与转录之间那行空白

[`tui-chrome/spec.md:196`](../../tui-chrome/spec.md) 当初把「状态行上方那一行还给转录」，并留下话：**「若真机上读起来转录与状态行贴太紧，那就是留一行空白的理由，届时改 `CHROME` 一处」**。

| 方案 | 代价 |
| --- | --- |
| A 加一行空白 | 转录少一行（`CHROME` 4 → 5） |
| B 不加 | 保持现状：虚线已经是分隔 |

➡️ 推荐 **B**：转录的每一行都比「透气」值钱，而且那里已经有一条虚线在分段。**但这条只有你在真终端上能判** —— `tui-chrome` 当初就是留给真机的。

## 待拍板 4：上下文占比要不要在接近满时变色

今天它永远 `MUTED`（一个读数）。可以加一档：超过某阈值时转 `WARN`。

➡️ 推荐 **不加**。05 的判据是「要你注意的 → 信号」，而占比是一个**读数**、不是一个事件；上下文真的满了，系统有自己的通道（压缩 / 翻页）。加了它，`WARN` 就开始兼差 —— 那正是这次 effort 在收的东西。

## 输入区：按 05 的决定执行，本票不再问

去掉整段 `BOLD`（`tui.rs:4515`），草稿归 `PLAIN`；**提示符 `❱` 仍是界面上唯一会动的专色**，也是唯一的焦点。顺带一条：[`tui-input-pulse/spec.md`](../../tui-input-pulse/spec.md) 的测试断言「草稿保住了 `BOLD`」（`tests/render_layout.rs:950-953`）要跟着改。
