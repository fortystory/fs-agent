# 字形语法的两档（prototype）

对应 [字形语法的两档](../issues/04-prototype-glyph-grammar.md)。**一次性素材**；对着真终端看：`python3 .scratch/tui-visual-language/prototype/glyph-demo.py`。

## 依据（来自 [终端能力边界](../research/01-terminal-capability-bounds.md)）

- `border::LIGHT_TRIPLE_DASHED` 的横竖**就是** `┄`(U+2504) 与 `┆`(U+2506) —— 与外壳手画的是**同一码位**（`ratatui-core/src/symbols/line.rs:6,16,144-148`）。**所以「框架一套虚线」这件事事实上已经成立，不需要换字符。**
- 浮层与外壳的唯一差别是：浮层带四个**实线角**与 T 形交叉（ratatui 没有 triple-dash 的角）。
- `┄ ┆ ─ │` 在 UCD 16.0 全是 **Ambiguous(A)**：宽度由上下文决定。本机实测 **Liberation Mono 有 `─` 而没有 `┄` / `┆`**；好在 Alacritty 与 xterm.js 默认自绘 U+2500–U+259F，风险被终端兜住一部分。

## 现状：两档的分界已经存在，只有两处越界

| 位置 | 字形 | 归哪档 |
| --- | --- | --- |
| 外壳竖线 / 横线 | `┆` / `┄` | 框架 ✓ |
| 页签条上下、标签之间 | `┄` / `┆` | 框架 ✓ |
| 轨迹页单位分隔线 | `┄` × width | 框架 ✓ |
| 浮层边框的横竖 | `┄` / `┆` | 框架 ✓（已同码位） |
| **浮层的角与交叉** | `┌┐└┘├┤┬┴┼`（实线） | **越界** ← 本票要定 |
| **详情小节线** | `── 名称 ──`（实线） | **越界** ← 本票要定 |
| markdown 主题分隔线 | `─` | 内容 ✓ |
| markdown 引用条 | `│` | 内容 ✓ |
| markdown 表格网格 | `─` / `│` / `─┼─` | 内容 ✓ |

## 待拍板 1：浮层的角

| 方案 | 角字符 | 代价 |
| --- | --- | --- |
| A 实角（现状） | `┌┐└┘` | 角与线不同族：虚线框上出现实线角，角读起来"很重" |
| B 空角 | `" "`（空格） | 四角有开口；但线本来就在断续，观感自洽。**不引入任何新字符**，宽度无风险 |
| C 点角 | `·`(U+00B7) | 角补上了；但引入非 box-drawing 字符，且 U+00B7 **也是 Ambiguous(A)** |

➡️ 推荐 **B 空角**：框架档的全部字符都来自 U+2500 块，空角维持这个一致性；ratatui 的 `border::Set` 四个角本来就能设成空格，**不需要自绘**；代价只是「四角开口」，而虚线框本来就是开口的。

## 待拍板 2：详情小节线归哪档

| 方案 | 字形 | 理由 |
| --- | --- | --- |
| A 留实线（现状） | `── 思考 ──` | 它分隔的是**浮层里的内容**，与 markdown 的分隔线是同一件事 → 内容档 |
| B 改框架虚线 | `┄┄ 思考 ┄┄` | 浮层里的线一律归框架 |

➡️ 推荐 **A 留实线**：「浮层里既有框架线（边框，虚线）又有内容线（小节，实线）」正是两档的意义 —— 分档判据是**这根线在分什么**，不是它待在哪个容器里。

## 待拍板 3：符号表

现状散落的字形（脚本第 ④ 段能看到实物）：

| 符号 | 位置 | 语义 |
| --- | --- | --- |
| `▸` | 思考行、工具行 | 有折起来的内容（可点开详情） |
| `▸` | todo 页 | 进行中 ← **同一个字符，两个语义** |
| `☐` / `✓` | todo 页 | 待办 / 已完成 |
| `❱` | 输入区 | 提示符 |
| `┃` / `┊` / `⋮` | 回合条 | 焦点 / 普通 / 截断 |
| `> [x] [ ] ● ○` | 问卷 | 光标 / 选中 / 单选 |
| `…` | 轨迹页消息 | 行内截断 |
| `┆` | 状态行 | 三段分隔（与外壳竖线同码位，语义不同） |

三件事要定：

1. **要不要立一张符号表**（一个语义一个具名常量，住 `wording.rs` 或新的 `glyphs.rs`）？今天这些字形散在 `wording.rs`、`tui.rs`、`todo.rs` 与 `editor.rs` 四处。
2. **`▸` 的双义**：拆开（todo 的「进行中」换字符），还是靠区域区分（todo 页里全是 todo 行，不会与转录混）？
3. **「可点」要不要标在注入行与消息行上**？它们今天也可点开详情，但行首没有 `▸`；加标记会挤掉正文列宽，还要动 [`trace-tab`](../../trace-tab/spec.md) 刚定的前缀形态。

➡️ 推荐：

1. **立表** —— 成本很低，而且 `scripts/tui-startup-check.py` 与一批测试都要引用这些字形，散着改容易漏。
2. **靠区域区分，不拆** —— 这正是 [语义色板](../issues/03-prototype-semantic-palette.md)「分域」的同一个思路；但在符号表里把这条双义**明写出来**，别让它当暗知识。
3. **不加**。`▸` 的真正语义是「**这里有折起来的东西**」，不是「这一行可点」：注入行与消息行显示的是全文、没有折叠，所以不该有它。这样「可点标记时有时无」就不是不一致了 —— 它是两个不同的语义。

## 内容档不动

`─` / `│` / `─┼─` 与 markdown 的一切保持现状。

## 与 `tui-startup-check.py` 的关系（选 B / A 的额外好处）

脚本钉了三个字形锚点：`MARK_ROW = "▄▀▀█"`（L76）、`BORDER_H = "┄"`（L81）、`BORDER_V = "┆"`（L82），判据是全屏横/竖虚线各 **≥3**（L740-746）。**本票的推荐方案一个都不改这三个字符** —— 改角（B）与留小节线（A）都不会让它红。
