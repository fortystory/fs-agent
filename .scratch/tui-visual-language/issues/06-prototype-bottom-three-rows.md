# 底部三条（状态行 / 提示行 / 输入区）

Type: prototype
Status: resolved
Part of: ../map.md
Blocked by: 03, 05

## 问题

维护者点名「状态行 / 提示行 / 输入区」是当前的观感痛点之一（[图](../map.md) 冻结项 7）。现状：

- **状态行**：整行单一 `DarkGray`（`src/render/tui.rs:3923-3938`），三段「模型 / 模式 / 上下文 n%」之间只靠 `│` 分，**没有层次**；窄档先丢模型、再丢模式、最后只剩上下文占比，**这一行永远在场**。
- **提示行**：同样整行 `DarkGray`，按**主列**宽度排版（`tui.rs:4529-4533`），于是 120 列屏只剩 79 列给提示、只看得见四条键位；`ctrl-o 左栏` 只在最宽档出现（`wording.rs:1150-1160`）。
- **输入区**：3–10 行、无边框、整段 `BOLD`，`❱ ` 提示符逐帧呼吸（`tui.rs:4514-4517`）。

要定：

- 状态行三段的分隔与层级：`│` 保留吗？标签（`模型` / `模式` / `上下文`）与值（模型名、模式名、百分比）怎么分色分层？上下文占比要不要在接近阈值时变色（那会牵动 [层级语言](05-grilling-hierarchy-and-selection.md) 与 [语义色板](03-prototype-semantic-palette.md)）？
- **状态行与转录之间那行空白要不要加**：[`tui-chrome/spec.md`](../tui-chrome/spec.md):196 明确把「读起来贴太挤」留作改 `CHROME` 一处的理由 —— 这一条对得上今天的问题吗？加一行的代价是转录少一行。
- 提示行的键位阶梯与屏宽的关系：要不要给 `ctrl-o 左栏` 更早的位置？还是反过来承认「宽屏才有」是对的？
- 输入区那整段 `BOLD` 与提示符的关系：「可输入」要不要换一种表达（层级而非加粗）？

## 产物

`.scratch/tui-visual-language/prototype/bottom-three-rows.md`：至少两档宽度（120×24 与 80×24）的帧草图（真渲染器 TestBackend 快照或手绘皆可）+ 逐项决定。宽度相关的结论要顺带记下**为它花掉几行转录**。

## 接受的边界

- **提示符呼吸本身**是 [`tui-input-pulse/spec.md`](../tui-input-pulse/spec.md) 的决定，「在跑」要不要换表达由 [「在跑」的反馈方式](10-grilling-busy-feedback.md) 定 —— 本票只做静态形态；
- 状态行的降级顺序（先丢模型、再丢模式、最后只剩上下文）是既有的宽度策略，不重开；
- 输入区的高度上下限与「转录最后一行优先」的地板是 [`docs/render.md`](../../docs/render.md) 的契约，不动。

## 作答

**已解决（2026-10-05，HITL：维护者看完两档实况后拍板）**。产物：[`prototype/bottom-three-rows.md`](../prototype/bottom-three-rows.md) 与 `prototype/bottom-rows-demo.py`（按 `hint_line` / `status_row` 的算法重算真实宽度）。

### 决定

1. **提示行跨整屏**。`panes.hints` 的宽度从**主列宽**改成**整屏宽**，左栏从「全高」改成「到提示行为止」。
   - 依据是算出来的：**全部 6 条 + 出口 + 状态词要 111 列**，而 120 列屏给提示行只有 79 列（41 列被左栏吃掉），80 列屏只有 51 列。
   - **代价（写进 spec）**：左栏页区少 1 行 —— 120×24 下 **15 → 14**；[`trace-tab`](../trace-tab/spec.md) 冻结项 14 的**公式不变**（页高仍撑满剩余高度），变的只是那个剩余值。
   - **这条推翻 [`sidebar-toggle`](../sidebar-toggle/spec.md) 与 [`trace-tab`](../trace-tab/spec.md) 写下的「全高左栏」**，`/to-spec` 时要回改两处。
2. **状态行三段分层**：标签（`模型` / `上下文`）用 `MUTED`，值（模型名 / 模式名 / `42%`）用 `PLAIN`，`│` 用 `CHROME`。整行仍属过程档，只是行内分出主次 —— 用的是 05 给的手段，没有新颜色。
3. **不加那行空白**：`CHROME` 保持 4。转录的每一行都比透气值钱，且那里已有一条虚线在分段。（[`tui-chrome/spec.md:196`](../tui-chrome/spec.md) 留的口子，判定为**不取用**。）
4. **上下文占比不加阈值色**：它是一个**读数**、不是事件，保持 `MUTED`；`WARN` 只留给诊断、hook 反馈与 `Severity::Warn`。
5. **输入区去掉整段 `BOLD`**（执行 [层级语言](05-grilling-hierarchy-and-selection.md) 的决定）：草稿归 `PLAIN`；**提示符 `❱` 仍是界面上唯一会动的专色、唯一焦点**。

### 给下游票 / spec 的落点

- **实现面**：`layout::Regions` 的 `hints` 矩形要跨屏；`draw_sidebar` 与 `draw_divide` 的高度改成到 `hints.y` 为止；`wording::hint_line` 的宽度来源换成屏宽，`wording.rs:1179-1186` 那段「宽屏带着左栏时提示行比屏窄 41 列」的注释与整条阶梯数字要**重算重写**。
- **`docs/render.md`**：外壳几何（`CHROME = 4`、左栏全高、提示行宽度）三处要改。
- **测试**：`tests/render_layout.rs` 里与提示行宽度、左栏高度有关的断言会大面积动；`tests/render_layout.rs:950-953`（草稿保住 `BOLD`）按决定 5 改。
- **[07 转录右缘与左栏](07-prototype-transcript-edge-and-sidebar.md)**：左栏高度的那 1 行是**本票**改掉的（为了提示行），07 展开左栏各页形态时以 14 行（120×24）为基准。
- **[10「在跑」的反馈方式](10-grilling-busy-feedback.md)**：提示行现在是全屏宽，如果那张票想往提示行上加「在跑」的信号，可用宽度是 120 列而不是 79 列 —— 这是个新多出来的空间。

### 未证实

`⌘` 这类符号没有引入；提示行跨屏后**在 40 列窄档**（无左栏）行为不变（本来就跨屏）。真实终端上左栏「短一行」的观感要在手工清单 **⑳** 与 **⑮** 两节留记录。
