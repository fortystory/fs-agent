# `/clear`：结束当前会话、开一个新的

Type: implement
Status: ready-for-agent
Blocked by: 07

> 规格：`.scratch/goal-loop/spec.md` §12。
> 它是 rollover（票 07）的**第二个入口**：一个由键盘触发，一个由阈值触发。**两段入口、一段机制** —— 这一票要钉死这一点，别长出两套「开新会话」的语义。

## 目标

给键盘一个「结束当前会话、开一个新的」的手势。

## 落点

- `src/cli.rs`：`/clear` 进 `Submission` 表
- 组装层：调用票 07 的 rollover 机制
- `tests/goal_loop.rs`

## 具体行为

1. **`/clear` = 结束当前会话、开一个新的**（进程不重启，渲染器与终端留着）。**不是**「清空上下文继续用」—— `.scratch/clear-command/seed.md` 原来那句措辞在文档收口时一并改掉（票 15）。
2. **名字保持 `/clear`**：与 DSH、Claude Code 的手势一致，肌肉记忆在。
3. **它复用票 07 的 rollover 机制**，但**不带压缩、不带摘要注入**：它不是阈值触发的，人是主动清场，没有「要带过去的历史」这回事。
   - 两个入口的差别就这一处，其余（收会话、组装、旧文件保留）**同一条代码路径** —— 这一票的测试要盯住它。
4. **旧会话留在磁盘上**，仍能被 `--continue` / `sessions` 找回；`--continue` 打开的是**最新的**那个。
5. **它是手势，不是工具调用**：与 `/undo` 的写回、模式循环同规矩 —— **手势本身不进事件流**。所以「清过场」这件事没有流上的痕迹，审计看的是**会话边界**（新会话的第一条 `SessionStarted`）。
6. **没有当前目标时也照常工作**：`/clear` 不依赖目标。

## 测试

- `/clear` 之后：当前会话换了（新 `session_id`、流从空开始），旧会话文件仍在磁盘上且完整；
- `--continue` 打开的是**新的**那个；
- 与票 07 的路径比对：两个入口调用的是同一个 rollover，差别只有「带不带摘要」；
- 手势不进流：`/clear` 前后事件流的 payload 种类里没有新东西；
- 端到端：`/loop` 跑着的时候 `/clear` 的行为要说清楚（这一票定：`/loop` 期间输入区禁用，所以 `/clear` 打不出来 —— 断言这一点）。

## 不做什么

- 不做 `/clear` 的参数（无参数，整条提交）。
- 不做「清掉当前目标」这个语义 —— 目标归属在旧会话的流上，新会话没有归属，直到下一次 `/loop`。
- 不改 `Pending::ClearDraft`（那个只清输入框草稿，与上下文无关）。
