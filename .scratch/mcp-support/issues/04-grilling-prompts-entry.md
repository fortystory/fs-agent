# grilling：prompts 模板的人机入口

Type: grilling
Status: resolved
Part of: ../map.md
Blocked by: —

## Question

**提示词模板**（prompts）的发起者是**人**，不是模型 —— server 声明一批带参数的模板，等人挑一个、
填参数、再把它变成这次会话的一条消息。可 fs-agent 今天**没有这个入口**：会话中途能发起东西的
只有 `/` 菜单（`/discuss`、`/goal-new`、`/loop`、`/clear`、`/undo` 那几个手势），而它们是**常量**，
不是运行时从外部 server 拉来的清单。

要定的是：

- **接进 `/` 菜单**？那菜单就得支持运行时条目（它今天是常量），而且要有地方填模板参数。
- **不做入口**：模板这一档明确不做，写进本图的 `Out of scope`（那就等于把「整个协议面」缩掉一块）。
- **只让模型能 list**（`mcp_list` 里带上模板名），模板的实际使用仍由人粘贴 —— 半条腿。

这条的答案会决定 `/` 菜单要不要长出一个「动态条目」的能力，而那是一件独立的事（与
`.scratch/multi-role-view/` 那类界面改动同族）。

## Answer

**接进 `/` 菜单** —— 也就是这个 effort 把「`/` 菜单支持运行时条目 + 一个填参数的界面」纳入了 scope。

今天 `/` 菜单的条目是**常量**（`/discuss` / `/goal-new` / `/loop` / `/clear` / `/undo` 那几个手势），
而 MCP 的模板清单是**运行时**从 server 拉的。所以这一步要动两处：

- 菜单的数据源从常量变成「常量 + 运行时条目」；
- 选中一个模板后要有地方填它的参数（`prompts/get` 带 arguments），再把结果变成这一次会话的
  一条消息。

**为什么不做成「只 list、人自己粘贴」**：那等于把模板的一半价值丢掉，而且模型看到的模板名与实际
可用性脱节 —— 不如明确把整件事做完。

**边界**（写进 spec 的实现决定）：

- 模板由**人**挑，**模型不自发调用** —— 这一条在图的 `Out of scope` 里，不因本票改变。
- 菜单的动态部分**不进工具表、不进前缀缓存**：它是界面层的东西，与 `mcp_list` / `mcp_call` 无关。
- server 不可用时，它的模板条目**不出现**（而不是出现后点开报错）—— 这是菜单元件的降级，与
  「工具仍在表里、调用才报错」那条冻结项不同，因为菜单本来就是运行时拉的。
