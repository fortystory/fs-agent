# TUI 外壳收干净：去外框、虚线化、详情居中与按位置滚动

外壳做减法：**拆掉那圈把一切框住的外框**，再拿掉状态行上方那条线，把剩下来的结构性框线换成**更沉的虚线**；详情覆盖层从「主列里居中」改成**屏幕居中**；覆盖层立着的时候，滚轮不再被它一口吃掉，而是**指针落在哪一块就滚哪一块**。

来源：2026-10-01 维护者的五条口头要求（一次 `/ask-matt` 会话的路由判定：单 session 可完成的 UI 改动，因此不经过 wayfinder 图，直接 spec + 票）。**未经过 grilling 的访谈轮**——五条要求本身就是决议，本文件只补它落到代码上的几何。

它**推翻**两处已落地的设计意图，落点都标在对应小节里：

- [`../tui-sidebar/spec.md`](../tui-sidebar/spec.md) §1 的「一圈外框 + 内部分隔线」（需求 1、2、3 只留后者，且改成虚线）；
- 同文件 §7 与 `tui-sidebar/issues/04-turn-rail.md` §2 的「前两者（详情、问题）吃掉一切指针」（需求 5 改成按位置分派）。

## 问题陈述

1. **那圈外框花了两行两列，回答的却是一个没人问的问题。** 终端本身就是界面的边界，外面再描一圈只是把内容往里挤：120×24 下主列每个方向少一格、转录少两行，而它挡不住任何人。
2. **状态行上方那条横线是三条里最没用的一条。** 它分隔的是「转录」与「一行读数」，而这两者本来就靠字形与缩进分得开；它占掉的那一行本来可以是转录。
3. **剩下的框线在深色终端上偏亮。** 统一用的 `DarkGray` 在常见配色里是 `#808080` 上下，作为「框架」它比内容还先被看见——维护者的原话是「颜色再深点」。同一批线全是实线，与界面上已有的虚线（回合条的 `┊`）也是两套语汇。
4. **详情覆盖层在主列里居中，看起来是偏的。** 主列被左栏切掉了 28–41 列，于是「居中」的框在**屏幕**上明显偏右；读一段正文时那点偏斜一直在。
5. **问题一立起来，滚轮就失灵。** `mouse()` 的前两段（详情、待答问题）直接 `return`，滚轮压根到不了转录：问卷占着底部输入区、转录明明还在上面露着，而指针无论停在哪儿，滚轮都只能挪问卷高亮；中间模态立着时，滚轮更是**任何位置都没有反应**。维护者要的是「在哪个部分滚动就滚动哪个部分」。

## 方案

- **外框离场**（§1）：外壳不再画 `Block`；内容区就是终端本身。端点交叉符 `┬ ┴ ├ ┤` 随之消失，竖分隔线从屏幕顶画到屏幕底。
- **状态行上方那条线离场**（§2）：主列的横线从三条减到两条（输入区上方、提示行上方），空出来的那一行**还给转录**，状态行紧贴转录最后一行。
- **剩余框架虚线化并把颜色压深**（§3）：结构性框线（竖分隔线、两条横线、页签条的上下线与其分隔符、`/` 菜单的框）统一用**浅三重虚线** `┆` / `┄`，颜色从 `DarkGray` 换成一个真彩暗灰常量。问题覆盖层与详情覆盖层也换虚线边框，但**保留各自的语义色**（黄、发言者色）——「更深」那条只针对本来就是灰的结构线。
- **详情覆盖层屏幕居中**（§4）：宽度的上限与边距照旧，居中基准从主列换成整屏。问题覆盖层**保持主列居中**（维护者点名的是详情）。
- **滚轮按位置分派**（§5）：覆盖层立着时，指针在它自己那块里就归它（问卷挪高亮、模态什么都不做），指针在转录上就滚转录。**点击的优先级一丝不变**。

## 实现决定

### §1 外框离场

`draw_shell` 不再调用 `draw_border`；`draw_border` 整个删除。外壳剩下的三笔是：竖分隔列、左栏（含页签条）、主列的横线。

**内容区就是终端**，所以 [`layout::plan`](../../src/render/layout.rs) 从

```rust
let inner = inner(area);          // 外框之内
```

改成直接用 `area`。随之：

- **`main_width(width) = width − 左栏总宽`**（原来还要减 `BORDER_COLUMNS`）。左栏隐藏时主列拿到 `width` 全部。
- **`BORDER_COLUMNS` 的用途收窄**：它不再是「外壳花掉的行列」，而是「**一个带框浮层**花掉的行列」。`layout::inner()` 保留原义（浮层内容矩形 = 外框内缩一格），问题覆盖层、`/` 菜单、详情覆盖层继续用它。它不再出现在 `plan()` 与 `main_width()` 里，rustdoc 要写明这层意思。
- **`Regions` 新增 `screen: Rect`**：整屏矩形（就是 `plan` 的入参 `area`）。它是 §4 详情居中的基准，也是「外壳不再有内缩」这件事在类型上留下的唯一痕迹。

**端点交叉符消失。** 因为再没有边框可以接：

- `draw_divide`：整列一律 `┆`（原 `┬ / │ / ┴` 三选一取消）。
- `paint_rule`：整行一律 `┄`（原 `├ … ┤` 取消），签名从 `(y, left, right)` 变成「画满 `left..right`」即可，两侧端点不再特殊处理。
- 主列横线的右端从 `area.right() − 1` 变成 `area.right()`（原来那一格是外框的右边框）。
- 页签条两条线的左端从 `sidebar.x − 1` 变成 `area.x`（原来那一格是外框的左边框）。

**降级阶梯不变**：`MIN_WIDTH` / `MIN_HEIGHT`（40×10）、左栏三档宽度（40 / 28 / 隐藏）、状态行三档、提示行按主列算——都不动。变的是它们之下那些矩形的坐标与高度。

### §2 状态行上方那条线离场，那一行还给转录

主列的横线由三条减到两条：`panes.input.y − 1` 与 `panes.hints.y − 1`。`panes.status.y − 1` 那条不再画。

**那一行不留在原处当空白**：留一个空白行等于「删了线、留着线的位置」，看起来像漏画。所以状态行紧贴转录的最后一行（`status.y == transcript.bottom()`），省下的一行整行还给转录。

纵向算术随之重排。设 `h` 为终端高、`ir` 为输入区行数：

```
转录行 tr = h − CHROME − ir
transcript = (x, 0, w, tr)
status     = transcript.bottom()          // 紧贴，中间不隔行
input.y    = status.bottom() + 1          // `bottom()` 是排他的，那条线正好占它这一行
hints.y    = input.bottom() + 1           // 同上

CHROME = 4   // 两条横线 + 状态行 + 提示行（原来是 7：外框上下 2 + 三条线 + 状态行 + 提示行）
```

`max_input_rows(height) = min(MAX_INPUT_ROWS, height − CHROME − 1).max(1)` 里的 `CHROME` 跟着变小，于是 **40×10 地板下输入区拿满 3 行、转录留 3 行**（原来是输入区 2 行、转录 1 行）。这是这条改动顺带买到的，把它当**预期值**钉住。

`Regions.transcript` 的 `y` 从 1 变 0；`Regions.status` / `input` / `hints` 的 `y` 都往下串。`draw_*` 全部从 `Regions` 读坐标，所以只有 `plan()` 与测试里的常量需要动。

### §3 剩余框架虚线化，颜色压深

**字形**：结构性框线统一用 **浅三重虚线**（`ratatui_core::symbols::line` 的 `LIGHT_TRIPLE_DASH_HORIZONTAL` / `..._VERTICAL`，即 `┄` / `┆`）。选三重而不是四重，是为了不跟**回合条**已有的 `┊`（四重竖，普通格）撞脸——那是另一套语义（一格一回合）。

| 落点 | 现状 | 改成 |
| --- | --- | --- |
| `draw_divide` 竖分隔列 | `│`（端点 `┬`/`┴`） | `┆` 全列 |
| `paint_rule` 两条横线 | `├ … ┤` | `┄` 全行 |
| `draw_tab_bar` 的上下线 | 同上 | 同上（走的就是 `paint_rule`） |
| `draw_tab_bar` 标签之间的分隔符 | `│` | `┆` |
| `draw_menu` 的 `Block` | `Borders::ALL` | `Borders::ALL` + `border_set(border::LIGHT_TRIPLE_DASHED)` |

**颜色**：新增一个常量，结构性框线全部改用它：

```rust
/// 结构性框线的颜色：比 `DarkGray` 再沉一档（`DarkGray` 在常见配色里 ≈ `#808080`）。
/// 深色终端上这是「框架退到内容后面」的取值；亮背景终端可能需要在这一点上调。
const CHROME_LINE: Color = Color::Rgb(0x4a, 0x4a, 0x4a);
```

它是这个界面里**第二处**真彩色（第一处是提示符的色相脉冲，`.scratch/tui-input-pulse/spec.md` §2b）：16 色 ANSI 里比 `DarkGray` 更暗的只有 `Black`，那在深色背景上等于消失，所以要一个明确的灰阶。

**弹窗保留语义色、只换虚线**：`draw_modal` 的框保持 `Color::Yellow`，`draw_detail` 的框保持发言者颜色（`view.detail.color`），两者加上 `border_set(border::LIGHT_TRIPLE_DASHED)`。理由是这两种颜色**在说话**（一个是「需要你动手」，一个是「这一行属于谁」），把它们调暗会伤到语义；维护者说的「更深」指那批本来就是灰的结构线。

**不动**：回合条的 `┊` / `┃` / `⋮`、滚动条、语法高亮、提示符的色相。

### §4 详情覆盖层屏幕居中

[`Regions::detail()`](../../src/render/layout.rs) 的居中基准从 `self.main` 换成 `self.screen`：

- 宽度不变（`main`-based 的 `detail_width()` 上限 135 与 `MODAL_MARGIN` 照旧）——**但要重新量一遍**：基准换成整屏后，`screen.width − MODAL_MARGIN` 在 120 列下是 116，仍小于 135，所以实际宽度照旧由边距封顶，与今天相同。
- 高度不变（`screen.height − BORDER_COLUMNS − DETAIL_MARGIN_ROWS`，外壳不再内缩之后比今天高 2 行，正文因此多两行）。
- 位置：`x = screen.x + (screen.width − width) / 2`、`y = screen.y + (screen.height − height) / 2`。
- 小到画不出正文时的 `None` 判据照旧（`width <= BORDER_COLUMNS` 或高度不够）。

**问题覆盖层（`modal()`）不动**：它保持主列居中（`self.main`）。维护者点名的是详情；问题覆盖层压掉左栏会盖住会话读数，那是 `tui-sidebar` §1 明确保下来的东西。两者因此**故意不同基准**，这一点写在两处 rustdoc 里，免得下一个人当成 bug 抹平。

### §5 覆盖层立着时，滚轮按位置分派

[`TuiState::mouse`](../../src/render/tui.rs) 的前两段不再「吃掉一切」：

**详情覆盖层**（不变）：它本来就整块占着指针，滚轮滚详情主体——这一条是对的，不动。

**待答问题**（改）：滚轮的落点决定它归谁，**点击的优先级不变**（覆盖层仍然先接点击）。

- `Pending::Questionnaire`（问卷占着底部块 `panes.input` 与页脚 `panes.hints`）：
  - 指针落在**底部块内**（`input ∪ hints`）→ 挪高亮（今天的 `questionnaire.move_highlight`）。
  - 指针落在**别处**（转录、左栏）→ 滚转录（`self.pane.wheel`）。
- `Pending::{Loop, Paste, ClearDraft, Exit}`（浮在主列中央的模态）：
  - 指针落在**模态矩形内** → 什么都不做（模态没有可滚的内容）。
  - 指针落在**模态外** → 滚转录。

为此 `TuiState` 新增 **`modal_rect: Option<Rect>`**，与已有的 `detail_rect` 同形、同一个纪律（**这一帧真的画了什么就记什么**）：`draw_modal` 在算出 `area` 之后记下它，跳过绘制的那些分支（`inner == 0`、`rows_available == 0`、`panes.modal()` 返 `None`）记 `None`。模态没画出来时，指针「在它里面」这件事不存在，滚轮因此落到转录上——这是诚实的答案。

**问卷为什么用 `input ∪ hints` 而不是记矩形**：问卷**没有边框**，它占的就是排版给底部的那两块；这两块本来就是 `Regions` 的字段，不必再引入一份会与排版漂移的记录。模态有边框，所以它记矩形。

命中判定一律用 `Rect::contains((column, row).into())`，与 `draw_detail` 关框那次点击同一个写法。

### §6 第二轮：真机反馈的两条微调（2026-10-01，票 07–08）

第一轮落地、维护者在真终端上看过之后，提了两条：

**（a）左栏身份从顶上下移一行。** 标记或文字身份原来紧贴屏幕顶上，太挤。新增
`layout::SIDEBAR_TOP_GAP`（= 1）：左栏的矩形从 `area.y + 1` 起、高度 `area.height − 1`，
而 `sidebar_content` 看到的内容行也是 `area.height − 1` —— **留白是花掉的行**，不是白得的，
所以高度阶梯照旧由「内容行够不够」决定。页签条与左栏各页都从 `sidebar` 派生，因此一起下移，
没有第二处算术；竖分隔列不动，仍从屏幕顶画到底。

这一条让阶梯在地板之上回到四档：`h ≥ 15` 标记 / `11–14` 文字身份 / `h = 10` 连身份都放下。
`h = 10` 的内容行是 9，正好是「页签条 + 上下文 / token / 回合」的地板 —— 第一轮里够不到的
「退到什么都不画」那一档，因为这一行的让出**又回来了**。

**（b）横线挨着竖线画，不把它截断。** 主列那两条横线原来从分隔列那一格起画，把那里的 `┆`
盖成 `┄`，竖线在视觉上断成三截。改成从**分隔列右边一格**起画：`left = divide + 1`，没有左栏
时就是 `area.x`（那一支不能顺手加一，否则无左栏的档位上第一列会空着）。于是竖线从屏幕顶贯通
到底，横线接在它旁边 —— 左栏页签条那两条线本来就是这么画的（它们画到 `divide` 为止、不含那一
格），现在两处一致了。

## 测试决定

- 布局仍用 `TestBackend` 断言（`tests/render_layout.rs` 的既有接缝：`buffer` / `screen` / `cells`），不需要 pty。
- **测试里的常量要跟着改**：`TRANSCRIPT_TOP` 从 `1` 变 `0`；`transcript_rows()` 那条「找 `┤` 定位主列第一条横线」的探针失效（端点符没了），改成**找第一条含 `┄` 且在主列内的行**，或者干脆按 `h − CHROME − ir` 算。这是本轮**唯一**一处「测试自己也建立在被推翻的写法上」的地方，要在票里点名。
- **新增/改写的用例**：
  1. 四个角上**没有任何边框字符**（`┌ ┐ └ ┘ │ ─` 在外壳帧里一个都不出现），且最外层的行/列是内容而不是框；
  2. 主列的横线**只有两条**，`status.y − 1` 那一行是转录的最后一行而不是线；
  3. 120×24 下转录行数 = `24 − 4 − 3 = 17`（原 14）；
  4. 40×10 下输入区 3 行、转录 3 行；
  5. 所有结构性框线是 `┄` / `┆`，且**颜色是 `CHROME_LINE`**；回合条的 `┊` 仍然是 `┊`；
  6. 问题覆盖层与详情覆盖层的边框是虚线、颜色分别是 `Yellow` 与发言者色；
  7. 详情覆盖层**在屏幕上居中**：左右留白相等（误差 ≤ 1），且**不等于**主列居中的位置（左栏存在时两者不同）；
  8. 滚轮：问卷立着、指针在转录上 → 视口上移；指针在问卷里 → 高亮移动而视口不动；模态立着、指针在模态外 → 视口移动；指针在模态内 → 视口不动。
- **要删/改的既有用例**：`the_wheel_is_ignored_while_a_question_is_up`（`tests/render_layout.rs`）这条断言**整个被推翻**，改成上面第 8 条；`tests/render_layout.rs` 里所有把 `│` / `├` / `┤` / `┬` / `┴` 当作锚点的断言（含 `transcript_rows()` 探针、`a_wide_terminal_draws_the_mark_the_sidebar_and_the_main_column`）要改成新字形或新的几何读法。
- **`scripts/tui-startup-check.py`**：它用 `BORDER_H = "─"` / `BORDER_V = "│"` 数横竖线来断言「窗格的框还在」，本轮之后屏幕上一根都没有。改成数 `┄` / `┆`（阈值照实测重取），并把注释从「每块一圈框」改成「外壳的分隔线与浮层边框」。`MARK_ROW` / `STATUS_ANCHOR` / 提示行那几处锚点不受影响。
- **手工清单**（`docs/tui-manual-checklist.md`）：加一节，覆盖「没有外框之后，左栏与主列在真终端里还分得开吗」「虚线在三重 / 四重之间读起来对不对」「`CHROME_LINE` 的深度在你自己的背景色上是否合适（不合适就调那一个常量）」「详情覆盖层居中看起来正不正」「问卷立着时在转录上滚一格」。

## 明确不做

- **键位表的任何增删**。
- **`MIN_WIDTH` / `MIN_HEIGHT` 地板的下调**：去掉外框后 40×10 确实更宽裕了，但那是另一件事，本轮不动。
- **问题覆盖层的居中基准**（保持主列，见 §4）。
- **问题的滚动**：中间的权限模态本来就没有可滚内容，本轮不引入。
- **主题 / 配色配置项**：`CHROME_LINE` 是一个常量，不是配置项；真彩色在非 truecolor 终端上的降级行为不处理（与提示符色相同一现状）。
- **plain / headless 渲染器的任何改动**、事件 schema、模型可见文本（ADR 0001 / 0005 冻结）。
- **轨迹 / 文件两个页签的内容**。

- **虚线用三重（`┄`/`┆`）而不是四重**（§3），为了与回合条的 `┊` 分开。
- **「颜色更深」只作用于灰的结构线**，弹窗保留自己的语义色（§3）。
- **只有详情覆盖层换基准**，问题覆盖层留在主列（§4）。
- **`CHROME_LINE` 取 `Rgb(0x4a, 0x4a, 0x4a)`**（§3）。这是对着「深色终端上框架比内容先被看见」这一个症状取的；换背景色就要换这个数，所以它单独是一个常量、写在它的 rustdoc 里。

### 实现期修正（2026-10-01 第一轮六张票落地时）

- **§2 的算术多算了一行。** `status.bottom()` / `input.bottom()` 是**排他的**，所以那些横线正好落在 `bottom()` 自己那一行上：`input.y = status.bottom() + 1`、`hints.y = input.bottom() + 1`（原文写的是 `+ 2`）。渲染时越界才发现，§2 与票 02 都已改掉。
- **票 01、02、03 是同批落地的**：三笔改的是同一片代码与同一批测试断言，拆开只会在同一批断点上返工三次。票 05 的测试改写与前四票同批完成。
- **票 04 的代价已实测**：详情覆盖层屏幕居中之后横向压住左栏、纵向压住底部输入区（120×40 下提示符落在框内）。这是「屏幕居中」的应有之义，判断留给真机清单 ⑳ 第 5 条。
- **票 05 里那条「模态没画出来时滚轮落到转录」的用例没有写**：`draw_modal` 的三个提前返回分支在 40×10 地板之上够不到 —— `main.width ≥ 40`、`main.height ≥ 10`，而模态高度总被 `rows_available` 夹在 `main.height` 之内。
- **`CHROME_LINE` 的实测深度**待维护者在自己的终端上确认，位置在 `docs/tui-manual-checklist.md` ⑳ 第 4 条 —— 这是本轮唯一一个随终端配色而变的取值。
- **测试那边顺带挖出的两处**：`panel_text` 里「页到哪儿结束」的守卫原来靠 `starts_with('│')`（外框），现在靠「这一行含 `┆` 或 `┄`」——主列的横线会把分隔列盖成 `┄`，所以两者都算证据；左栏的高度阶梯（「先退身份、再丢字段」）在后几档落到了 40×10 地板以下，那几档**够不到了**，用例按可达的档重取。
