# 动态工具注册与「只读」标记的可信度策略

Type: grilling
Status: closed
Blocked by: 03, 05

## Question

ratify 第 3 条翻案把「自定义工具注册」加进了范围。**这一条与已定的扩展档位 (iii) 直接冲突** —— (iii) 的原文是"**不**做配置驱动的动态加载（MCP / 插件）"。所以档位已被 superseded 为「hook 挂载点 **+** 动态工具注册」。本票要把新增的那一半定形。

**本票的核心不是"怎么加载"，而是"加载进来的东西能不能被信任"。**

1. **可信度策略（必答题）。** 工具面一旦不再编译期封闭，「只读」这个副作用标记就成了**不可信输入**。而并行判定规则是「按有无副作用打标，只读并发、有副作用串行」—— 综述从**五个独立数据点**收敛出的共识（Claude Code 明文规则、Gemini 默认并发但强制 `replace`/`write_file` 串行、Codex 默认串行、Cline 按模型家族开关、Continue 只对只读开放）。一个动态注册的工具**谎报只读**，就会让两个写操作并发。
   候选策略：
   - (a) 动态工具**一律默认串行**，只读需显式声明 + 首次人工确认；
   - (b) 声明即信任（明确放弃这条防线，并在文档里说清）；
   - (c) 动态工具**不可并发**，其副作用标记不参与并行判定。

2. **声明格式。** 综述的候选是「额外工具 = 一个 shell 命令 + 参数 schema」。schema 用什么表示（JSON Schema？）？与票 03 的内建工具注册表是**同一个数据结构**，还是两套？

3. **命令的解析与权限。** 动态工具最终落到 shell 命令，那么综述第 5 节那条「**用语法分析而非字符串匹配**来判定 bash 权限」（opencode 用 tree-sitter 解析命令 + 一张 arity 字典）是否也适用？还是说动态工具被视为受信任的本地扩展、走另一条路？

4. **命名空间。** 综述的反向警告：「工具一多模型越容易选错」；Anthropic 建议做命名空间（Amp / Claude Code 都用 `mcp__<server>__<tool>`）与工具合并。约定要不要现在就定？

5. **明确不做**：**MCP client 本身**（ratify 第 2 条已砍）。本票只做"本地声明的自定义工具"，不实现 MCP 协议。

**依赖说明**：必须在票 03（内建工具 trait / 注册表 / 副作用标记）与票 05（hook 与权限门的次序）之后 —— 可信度策略是在权限门里执行的，声明格式复用 03 的注册表。
