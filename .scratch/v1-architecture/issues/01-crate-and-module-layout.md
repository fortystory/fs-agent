# Crate 与模块布局

Type: grilling
Status: closed

## Question

决定 `fs-agent` 的 crate 与模块骨架。这是其余所有接缝的落脚点。

要回答：

1. **单 crate 还是 Cargo workspace？** 注意这是自用的单一二进制，workspace 的价值（多产物、编译隔离、多消费者）可能不存在。
2. **顶层模块边界在哪？** 综述隐含的候选是：agent loop、tools、providers、permissions、context、session、cli。**这些名字来自综述，不是最终答案**——请按你实际想要的切法定。
3. **二进制入口与库入口是否分离**（`main.rs` + `lib.rs`）？分离的好处是端到端测试能直接驱动循环、不经过 CLI 参数解析——这与综述切片 9（mock provider + e2e）直接相关。

答案定到：**模块列表 + 每个模块职责一句话 + 依赖方向（谁可以依赖谁）**。

不要定到文件级，也不要定到逐个函数签名（本图整体是边界级，见 map 的 Notes）。

## 已翻案的范围会落在这张票上

ratify 后新增了票 09–14，它们的接缝都要在模块列表里有位置。尤其两条会**反过来约束本票**：

- **一条渲染接缝**（票 13）—— 循环吐结构化事件，由 plain / TUI 两个渲染器消费，且 headless 要求 stdout 纯净。所以"输出"不能是一个模块内的 `println!`。
- **子 agent**（票 14）—— 若它做成一个 `task` 工具，那么循环本身必须**可重入**（同一进程里能跑第二个独立会话），这对模块边界与状态归属有直接影响。

其余四项也各需要一个落点：skills（票 09）、硬 plan 模式（票 10，复用权限门）、动态工具注册（票 11，落在注册表与权限门之间）、repo map（票 12，落在工具层与上下文预算之间）。
