# 渲染接缝：结构化事件 + plain / TUI 双消费者（含 headless 共存）

Type: grilling
Status: closed
Blocked by: 01, 05

## Question

ratify 第 10 条翻案把「全屏 TUI、状态栏、diff 语法高亮」加进范围。**这不是纯外观 —— 它给架构加了一条渲染接缝**，而票 01（crate 与模块布局）必须给它留位置。

**为什么有架构代价**：三个需求不能靠 `println!` 同时满足 ——

- 综述切片 8/14 要求 headless 模式下 **stdout 只放结果、日志走 stderr**（否则无法管道化）；
- 综述第 13 节的最小可用要求流式输出 + 每个工具调用一行可读摘要；
- 现在还要一个全屏 TUI（alt screen、可折叠工具输出、diff 语法高亮、状态栏显示 token / 花费 / 权限模式）。

结论：循环必须吐**结构化事件**，由两个渲染器分别消费。

要回答：

1. **事件的形状与总线数量（本票最关键的接缝问题）**。一次会话要发哪些事件（模型文本增量、工具调用开始/结束、权限询问、token/费用更新、循环终止原因……）？它与票 05 的事件 / hook 接缝**是同一总线还是两条**？
   - 合成一条：hook 消费者会看到渲染细节，扩展面被污染；
   - 合成两条：会出现两套事件类型，且顺序一致性要额外保证。
   这个取舍必须显式做出。
2. **进程模型**。综述记录 **opencode 把 TUI 与 agent server 拆成两个进程**（client/server，TUI 可替换、可远程）。v1 跟不跟？还是同进程内的两个渲染器？
3. **终止原因的表达**。综述推荐照抄 Cline 的显式枚举：`completed | max_iterations | aborted | mistake_limit | error` —— 比布尔"完成没完成"信息量大得多，也让日志与 eval 能区分"正常收尾"与"撞墙退出"。这直接喂给状态栏，也对上票 02 的终止判断。
4. **一个新的事实需求**：TUI 库选型（ratatui 的当前状态、依赖重量、与 tokio 的配合方式）。票 08 的产物没覆盖，本票可能需要**再派一次 research**。
5. **明确不做**：diff 语法高亮之外的编辑器能力（不做内置编辑器）。
