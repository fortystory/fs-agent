# 31: 权限模态在一次被取消的运行之后留在屏上

**What to build:** 把票 29 的「顺带发现（未改，留给需要时）」升成一张票。一次运行被取消时，如果当时有权限询问开着，弹窗**不会被撤下**：它一直显示到用户按任意键，而那个键回答的是**一个已经没有接收方的询问**——静默失败，之后草稿恢复，看起来像「这个键没反应」。

- [x] **根因**：模态的存亡跟着「有没有人回答」走，而不是跟着「这次运行还在不在」走。取消让运行结束，但循环从没告诉前端「那个问题作废了」，于是它继续为一个不存在的接收方收键。
- [x] **修法方向**：「这次运行的回合结束」与「问题属于哪次运行」对上。两条现成的路：给 `Ask` 加一条作废通道（循环收尾时显式撤回），或让前端把 `RunState { running: false }` 的到达读成「作废所有在飞询问」。后者复用票 29 刚建立的通道，代价是它把两件事捆在一个信号上，取哪条取决于实现时哪边更诚实。
- [x] **`Ctrl-C` 不在这个缺口里**：它在弹窗之前处理，空闲时直接退出（票 29 已定），所以这条只关于「那个键被谁接走」，不要顺手重排键位优先级。
- [x] **测试**：运行中途取消且有 `Ask` 在飞时，前端不留模态；其后第一个键不被已作废的询问吃掉（按现状它会静默失败）。

## Comments

**2026-09-22（补记）** 票 29 把这处写成评论区里的一句「留给需要时」。仓库既有先例不这么处理：tui-layout 票 12 把完全同类的问题（丢掉 reply sender ⇒ 询问静默变成拒绝）当缺陷修掉并加了守卫。而「问题属于哪次运行」正是票 29 自己那条原则的另一面——「循环在不在跑东西，只有循环自己知道」——所以它有资格进 tracker，而不是留在一条评论里等需要它的人刚好读到。

**与票 29 的边界**：票 29 修的是「空闲的 `Ctrl-C` 被吞」（键盘死了）；这一票修的是「作废的询问继续收键」（键去了错的地方）。同一个根因家族，两条不同的症状，所以分两张票而不是回改票 29。

**2026-09-22（实现）** 走了票面两条路里的**第二条：`RunState { running: false }` 撤回在飞询问**。票面担心的「把两件事捆在一个信号上」经检查不成立：询问只可能在运行内部发出（权限门在回合里问、计划冲突也在回合里问），所以「运行结束 ⇒ 没有活着的询问」是**可靠推导**而非巧合。第一条路（给 `Ask` 加作废通道 + id + 撤销守卫）更精确，但在这里换不来任何东西，只是多一个通道和一个 id 的生命周期要维护。

落点只有一处，`TuiState::request` 的 `RunState` 分支：

```rust
if !running && matches!(self.pending, Some(Pending::Loop { .. })) {
    self.pending = None;
}
```

**只撤 `Pending::Loop`**，不碰渲染器自己的两种确认（超长粘贴、`Esc` 清空草稿）——它们不是这次运行的问题，而且只可能在循环空闲时出现。**丢掉 sender 而不是替它作答**：这正是「没有人在等」的诚实读法；万一还有持有者，它按既有的 `unwrap_or(Deny)` 得到安全答案。

**两条测试**（都先红后绿）：

- `tests/render_tui.rs::a_cancelled_run_takes_its_unanswered_question_with_it` —— 行为面：运行中 Esc 是取消手势不是作答，运行结束后下一个键必须重新**编辑草稿**而不是回答那个陈旧问题。红的时候正是预测的形态：`left: Some("")`（`x` 被吃掉，提交了空串）、`right: Some("x")`。
- `tests/render_layout.rs::a_cancelled_run_leaves_no_overlay_behind` —— 渲染面：`draw_frame` 出的帧里先有「权限询问」，运行结束后不再有。这条自带守望（先断言覆盖层确实在），所以不会因为「根本没画出来」而假绿。

**变异检验**：把 `!running` 改成 `false`，两条**都转红**；恢复后都绿 ✓。

**基线**：`cargo test --all-targets` **601 passed / 0 failed**；`cargo clippy --all-targets` 干净。

**代价（已知并接受）**：撤回靠「运行边界到达」这个时刻。取消与 `RunState { running: false }` 之间有一个窗口，恰好落在窗口里的那一次按键仍会打到陈旧模态上（随后模态就被撤下）。窗口的长度是循环回到等待态的那一小段，不是用户可感的时间；要让这个窗口归零就得走第一条路（作废与 drop 同步）。**这条不阻塞**，因为症状从「键被永久吞掉」降级为「一次按键没效果」。
